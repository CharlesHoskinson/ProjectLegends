# Graphify Enrichment QA Layer Plan: ProjectLegends

## Objective

Build a deterministic QA layer for ProjectLegends Graphify enrichment. The layer must prove that the enriched graph correctly maps:

* public `legends_*` APIs
* `docs/architecture/capability_truth.json`
* `docs/architecture/2026-06-08-public-capability-truth-matrix.md`
* proxy `MsgType` usage
* `engine_dispatcher.cpp` cases
* tests and CMake target/source edges

The enrichment should be treated as an overlay on top of `graphify-out/graph.json`, not as manual edits to Graphify output.

## Planned Artifacts

Implement these files:

* `scripts/enrich_graphify_projectlegends.py`
  * Reads source, CMake files, existing capability docs, and `graphify-out/graph.json`.
  * Emits `graphify-out/projectlegends-enrichment.json`.
  * Emits `docs/architecture/graphify-enrichment-report.md`.
* `scripts/check_graphify_enrichment.py`
  * Validates the overlay against repo sources and Graphify output.
  * Exits nonzero on drift, missing evidence, dangling edges, or stale inputs.
* `docs/superpowers/reviews/2026-06-08-graphify-enrichment-qa.md`
  * QA handoff generated by the implementation phase.
* Optional schema: `scripts/schemas/projectlegends_graphify_enrichment.schema.json`.

The overlay JSON must be deterministic: stable ordering, normalized slash paths, stable node IDs, and a top-level `schema_version`.

## Node And Edge Contract

Use stable ProjectLegends IDs:

* `pl__api__<legends_name>`
* `pl__capability__<legends_name>`
* `pl__matrix_row__<legends_name>`
* `pl__file__<repo_path>`
* `pl__function__<repo_path>__<function>`
* `pl__msgtype__<MsgTypeName>`
* `pl__dispatcher_case__<MsgTypeName>`
* `pl__test__<repo_path>__<test_name_or_symbol>`
* `pl__cmake_target__<target_name>`
* `pl__preset__<preset_name>`

Required edge labels:

* `declared_in`
* `implemented_by`
* `proxied_by`
* `documented_by`
* `has_capability_truth`
* `uses_msgtype`
* `handled_by_dispatcher_case`
* `returns_msgtype`
* `covered_by_test`
* `source_of_target`
* `links_to_target`
* `built_by_preset`
* `validated_by`

## Gate 0: Input And Freshness Gate

Goal: prove the graph and source inputs are available and parseable before validating semantics.

Validator:

```powershell
python scripts/check_graphify_enrichment.py --repo . --overlay graphify-out/projectlegends-enrichment.json --gate inputs
```

Invariants:

* `graphify-out/graph.json` exists and parses as JSON.
* `graphify-out/manifest.json` exists and includes all critical files:
  * `include/legends/legends_embed.h`
  * `src/legends/legends_embed_api.cpp`
  * `src/legends_proxy/proxy_api.cpp`
  * `src/engine_host/engine_dispatcher.cpp`
  * `include/legends_ipc/message_types.h`
  * `include/legends_ipc/messages.h`
  * `docs/architecture/capability_truth.json`
  * `docs/architecture/2026-06-08-public-capability-truth-matrix.md`
  * `CMakeLists.txt`
  * `CMakePresets.json`
* Manifest hashes or mtimes are not older than source inputs. If Graphify metadata is stale, fail with a direct command to rerun Graphify.
* Overlay contains `schema_version`, `generated_at`, `source_hashes`, `nodes`, `edges`, and `summary`.

Graphify command:

```powershell
& "$env:APPDATA\Python\Python314\Scripts\graphify.exe" update . --no-cluster
```

Failure modes:

* Graphify has not been run.
* Graphify output is stale after source changes.
* Required source files moved.
* Windows backslash paths make overlay IDs nondeterministic.

Codex audit focus:

* Confirm freshness checks compare the same path format that Graphify records.
* Confirm the validator fails closed when `graphify-out` is missing.

## Gate 1: Public API Inventory Gate

Goal: prove every public C API export has exactly one enriched API node.

Validator:

```powershell
python scripts/check_graphify_enrichment.py --repo . --overlay graphify-out/projectlegends-enrichment.json --gate api-inventory
```

Invariants:

* API list is parsed from `include/legends/legends_embed.h` using the same rules as `scripts/check_capability_matrix.py`.
* Current expected count is 50 public `legends_*` exports.
* No duplicate API names.
* Every API has:
  * one `pl__api__<name>` node
  * one `declared_in` edge to `include/legends/legends_embed.h`
  * one `implemented_by` edge to `src/legends/legends_embed_api.cpp#<name>`
  * one `proxied_by` edge to `src/legends_proxy/proxy_api.cpp#<name>`
* No overlay API node exists for a name absent from the header.

Failure modes:

* Header export added without enrichment.
* Regex parser misses a multiline declaration.
* Overlay contains stale APIs removed from the header.

Codex audit focus:

* Compare parser behavior against `check_capability_matrix.py`; avoid two subtly different export parsers.

## Gate 2: Capability Truth And Matrix Sync Gate

Goal: prove the enriched graph reflects the JSON source of truth and the Markdown matrix.

Validator:

```powershell
python scripts/check_capability_matrix.py --repo .
python scripts/check_graphify_enrichment.py --repo . --overlay graphify-out/projectlegends-enrichment.json --gate capability-sync
```

Invariants:

* Every API has exactly one `has_capability_truth` edge to `pl__capability__<name>`.
* Every API has exactly one `documented_by` edge to `pl__matrix_row__<name>`.
* Direct/proxy statuses in overlay equal `capability_truth.json`.
* Direct/proxy statuses in overlay equal the Markdown matrix.
* Every `evidence_files` entry exists and is linked by `validated_by` or evidence metadata.
* `proxy-partial` entries must carry a non-empty reason.
* `proxy-supported` entries must list dispatcher evidence unless explicitly modeled as shared-memory-only and marked partial.

Failure modes:

* JSON and Markdown drift.
* Status updated but graph overlay still reports old status.
* Evidence path typo.
* Partial status without a reason.

Codex audit focus:

* Verify mount/unmount remain `proxy-supported`.
* Verify `capture_rgb` and `capture_audio` remain partial until engine-host SHM production is real.

## Gate 3: Proxy MsgType And Dispatcher Parity Gate

Goal: prove supported proxy APIs have a complete IPC path.

Validator:

```powershell
python scripts/check_graphify_enrichment.py --repo . --overlay graphify-out/projectlegends-enrichment.json --gate ipc-parity
```

Invariants:

For every API with `proxy_status == "proxy-supported"`:

* Proxy body does not directly return `LEGENDS_ERR_NOT_SUPPORTED`.
* Proxy body references at least one request `MsgType`.
* Each request `MsgType` exists in `include/legends_ipc/message_types.h`.
* Each request `MsgType` has a dispatcher `case MsgType::<Name>:` in `src/engine_host/engine_dispatcher.cpp`.
* Each dispatcher case returns the paired response `MsgType`.
* Dispatcher case calls the expected direct `legends_*` API, except documented aliases such as `legends_force_destroy` mapping to destroy semantics.

For every API with `proxy_status == "proxy-missing"`:

* Proxy body must directly return `LEGENDS_ERR_NOT_SUPPORTED`, or the manifest must explicitly record why it is missing.
* No overlay path may claim full proxy support.

For every API with `proxy_status == "proxy-partial"`:

* Overlay must name the missing boundary, for example shared-memory producer, extended-key semantics, or incomplete engine-host lifecycle.

Failure modes:

* Proxy sends a request that dispatcher does not handle.
* Dispatcher case exists but returns the wrong response type.
* Proxy-supported manifest entry masks unsupported behavior.
* Alias behavior is treated as full parity without a documented caveat.

Codex audit focus:

* Read `src/legends_proxy/proxy_api.cpp` and `src/engine_host/engine_dispatcher.cpp` manually for APIs promoted to `proxy-supported`.
* Check `MountDriveReq` and `UnmountDriveReq` deserialization and response serialization.

## Gate 4: IPC Message Schema Gate

Goal: prove `MsgType` enum entries, message structs, and serializer contracts are internally consistent.

Validator:

```powershell
python scripts/check_graphify_enrichment.py --repo . --overlay graphify-out/projectlegends-enrichment.json --gate ipc-schema
```

Invariants:

* Every request enum has a paired response enum unless it is a control/event message explicitly allowlisted.
* Every request/response type referenced by proxy or dispatcher has a matching struct in `include/legends_ipc/messages.h`.
* Every struct used by dispatcher has `serialized_size`, `serialize`, or `deserialize` members as appropriate.
* Variable-size payload request types are tagged in overlay metadata.
* Dispatcher default case returns `ErrorResponse`.

Failure modes:

* New enum added without message struct.
* Struct added but not used by proxy or dispatcher.
* Variable payload lacks explicit bounds validation.
* Control messages are accidentally treated as public API capability messages.

Codex audit focus:

* Do not accept string-name pairing alone for variable payload safety. Inspect deserialize bounds behavior for each variable payload.

## Gate 5: Test Coverage Mapping Gate

Goal: prove graph claims about test coverage are evidence-based, not just string mentions.

Validator:

```powershell
python scripts/check_graphify_enrichment.py --repo . --overlay graphify-out/projectlegends-enrichment.json --gate tests --strict-tests warn
```

Initial mode should be `warn`; move to `--strict-tests fail` after the first coverage baseline is clean.

Invariants:

* Test nodes come from `tests/**`, `engine/tests/**`, and CMake test targets.
* A test coverage edge must be based on one of:
  * direct call to the public API
  * direct dispatcher invocation with `MsgType`
  * proxy API call
  * explicit test metadata comment such as `GRAPHIFY_COVERS: legends_mount_drive`
* A plain text mention in comments or docs is not enough.
* Every `proxy-supported` API must have a test edge or an explicit waiver in overlay metadata.
* Every dispatcher case for a public API must have a dispatcher/proxy/ABI test edge or a waiver.
* Disabled tests must be represented as `coverage_status: disabled`, not passing coverage.

Failure modes:

* Test coverage inflated by comments.
* Disabled tests counted as active coverage.
* ABI-only coverage mistaken for IPC proxy coverage.
* Supported API has no test path.

Codex audit focus:

* Review all waivers. Waivers should be rare, named, and tied to a follow-up issue or plan item.

## Gate 6: CMake Target And Build Variant Gate

Goal: prove enriched CMake edges match the actual build graph for dev and IPC variants.

Validator:

```powershell
python scripts/check_graphify_enrichment.py --repo . --overlay graphify-out/projectlegends-enrichment.json --gate cmake
```

Supporting commands:

```powershell
cmake --preset dev
cmake --build --preset dev
cmake --build --preset ipc
python scripts/verify_gpl_isolation.py
```

Invariants:

* Overlay includes CMake target nodes for relevant targets:
  * `legends_app`
  * `project_legends`
  * `legends_embed`
  * `legends_proxy`
  * `legends_engine_host`
  * `legends_abi_test`
  * `legends_ipc_integration_tests`
* Source edges agree with CMake declarations and generated build metadata where available.
* `src/app/runtime_host.cpp` is linked into the app/library target that owns RuntimeHost.
* `src/legends_proxy/proxy_api.cpp` is part of the IPC/proxy target.
* `src/engine_host/engine_dispatcher.cpp` is part of the engine-host target.
* IPC preset does not link proprietary app targets directly against GPL engine internals, subject to the repo's GPL isolation validator.

Failure modes:

* CMake parser misses variable-expanded target sources.
* Graph says a source is built in IPC but build metadata disagrees.
* IPC target silently links a forbidden engine target.
* Windows-specific tool path requirements make IPC build unverified.

Codex audit focus:

* Prefer build metadata over handwritten CMake parsing when they disagree.
* Verify the GPL isolation check is meaningful, not just target-name matching.

## Gate 7: Graph Overlay Integrity Gate

Goal: prove the overlay is a valid graph that can be consumed by tools and audited by humans.

Validator:

```powershell
python scripts/check_graphify_enrichment.py --repo . --overlay graphify-out/projectlegends-enrichment.json --gate graph-integrity
& "$env:APPDATA\Python\Python314\Scripts\graphify.exe" diagnose multigraph --json --max-examples 5
```

Invariants:

* All node IDs are unique.
* All edge IDs are unique or deterministically derived.
* Every edge source and target exists.
* Every file path node points to an existing repo file or an allowlisted generated file.
* Every overlay file node has a corresponding Graphify manifest entry unless it is generated by the enrichment step.
* Overlay is deterministic: rerunning enrichment without source changes produces identical JSON bytes.
* Summary counts match actual nodes/edges by type.

Failure modes:

* Dangling edge after a source file rename.
* Non-deterministic ordering causes noisy diffs.
* Generated report and JSON disagree.
* Overlay claims Graphify coverage for files Graphify never indexed.

Codex audit focus:

* Rerun enrichment twice and compare file hashes.
* Inspect any allowlisted generated files.

## Gate 8: CI And QA Handoff Gate

Goal: make the enrichment QA repeatable and visible.

Validator:

```powershell
python scripts/enrich_graphify_projectlegends.py --repo . --graphify graphify-out/graph.json --out graphify-out/projectlegends-enrichment.json --report docs/architecture/graphify-enrichment-report.md
python scripts/check_graphify_enrichment.py --repo . --overlay graphify-out/projectlegends-enrichment.json --strict
python scripts/check_capability_matrix.py --repo .
python scripts/check_conflict_markers.py --path .
git diff --check
```

CI wiring:

* Add a blocking step to `.github/workflows/sprint2-checks.yml`.
* Trigger on:
  * `include/**`
  * `src/**`
  * `tests/**`
  * `scripts/**`
  * `docs/architecture/**`
  * `CMakeLists.txt`
  * `CMakePresets.json`
  * `.github/workflows/sprint2-checks.yml`
* CI should run the source-derived enrichment and validator.
* CI should not depend on committing the large `graphify-out/graph.json` unless the team explicitly decides to version Graphify output.
* Local audit can additionally run `graphify.exe update` and compare the overlay against `graphify-out/graph.json`.

QA artifact must include:

* Gate status table.
* Input files and output artifacts.
* API counts by status.
* IPC request/dispatcher coverage counts.
* Test coverage counts and waivers.
* CMake target/source count summary.
* Commands passed.
* Commands failed or blocked.
* Top Codex audit targets.

Failure modes:

* CI validates overlay generated from stale committed JSON.
* CI path filters omit docs or CMake changes.
* QA artifact claims full coverage while strict test gate is still warn-only.

Codex audit focus:

* Confirm CI regenerates the overlay before checking it.
* Confirm the QA artifact records warn-only gates clearly as caveats, not PASS.

## Recommended Implementation Order

1. Extend the existing capability parser logic into shared helpers or import-safe functions.
2. Implement `enrich_graphify_projectlegends.py` for API, capability, proxy, dispatcher, and message edges.
3. Implement `check_graphify_enrichment.py` gates 0 through 4.
4. Add test coverage mapping in warn mode.
5. Add CMake target/source mapping using CMake files plus build metadata.
6. Add graph integrity determinism checks.
7. Wire the source-derived checks into `sprint2-checks.yml`.
8. Generate the QA handoff artifact and have Codex audit the top findings.

## Success Criteria

The enrichment sprint is complete only when:

* `python scripts/check_graphify_enrichment.py --repo . --overlay graphify-out/projectlegends-enrichment.json --strict` passes.
* `python scripts/check_capability_matrix.py --repo .` passes.
* `python scripts/check_conflict_markers.py --path .` passes.
* `git diff --check` passes.
* The QA artifact lists any non-strict or warn-only gate explicitly.
* Codex can answer: "For any `legends_*` API, show declaration, direct implementation, proxy status, IPC request, dispatcher case, tests, and build target evidence."
