# Local Preflight Design (2026-06)

## Summary

Research synthesis on designing a `preflight` target that mirrors Project Legends' mandatory CI tier on a developer machine in minutes. Raw notes with full quoted passages: `raw/research/local-preflight-design.md`. Six sources, all retrieved 2026-06-10: the cmake-presets(7) manual, pre-commit.com, Lefthook docs + README, the just Programmer's Manual, the NixCI local-first-CI post, and GitHub's Scripts to Rule Them All.

Current repo state this applies to: no preflight command exists — replicating the mandatory tier takes five manual steps across four workflows ([[Local Dev Loop]], "Replicating the mandatory CI tier locally"). The mandatory tier is 4 build/test configurations (`ci.yml:36-77`, `ci.yml:95-127`, `ci.yml:189-207`, `ci.yml:707-738`), the nine sprint2 script steps (`sprint2-checks.yml:44-85`), include rules (`module-dag.yml:64-66`), and the C ABI check (`ci.yml:406-430`). `CMakePresets.json` already declares schema `"version": 6` and `cmakeMinimumRequired` 3.25 (`CMakePresets.json:2-7`) with nine configure presets plus build/test presets — but **no** `workflowPresets` array, and CI bypasses presets entirely with raw `-D` flags (`ci.yml:64-71`; [[Local Dev Loop]]). The only hook is `.githooks/pre-commit`, a 14-line bash script running one of eleven check scripts, opt-in via `git config core.hooksPath .githooks`, documented only in its own comment (`.githooks/pre-commit:3, 7`). `CONTRIBUTING.md` mentions no check script and no hook. There is no Makefile, justfile, or task runner at the root.

## Applicable practices

### 1. One entry point that both CI and developers run — and CI must actually run it

The core principle: "Local-first CI means designing your checks to run on your machine first, and then running the same checks remotely. For example: make a script like ./ci.sh and run it both locally and remotely." ^[from https://blog.nix-ci.com/post/2026-03-09_ci-should-fail-on-your-machine-first (retrieved 2026-06-10)] The direction of mirroring matters: GitHub's pattern has the CI server call the same script developers call — "Your test are run simply by calling script/test" from `script/cibuild`, with each script "responsible for a unit of work. This way they can be called from other scripts." ^[from https://github.com/github/scripts-to-rule-them-all (retrieved 2026-06-10)] Divergence is the documented failure mode: "in practice developers will notice sooner or later that they can ignore what CI does locally because CI will pass remotely anyway. At that point local-first CI becomes extra overhead without any benefit." ^[from https://blog.nix-ci.com/post/2026-03-09_ci-should-fail-on-your-machine-first (retrieved 2026-06-10)] The remote run stays mandatory regardless: "It is essential that we also still run CI remotely because developers can forget to run it locally first." ^[from https://blog.nix-ci.com/post/2026-03-09_ci-should-fail-on-your-machine-first (retrieved 2026-06-10)]

**Applicability to Project Legends:** the repo currently has the inverse architecture — gate logic lives in workflow YAML steps (`sprint2-checks.yml:44-85` lists nine `python scripts/check_*.py` invocations as separate YAML steps; `ci.yml:414-419` inlines the ABI compile) and nothing local calls it. A `scripts/preflight.py` (Python is already the gate-script language, and `sprint2-checks.yml:41-42` already pip-installs `pyyaml`) that runs the script gates + include rules + ABI check + the chosen build/test presets gives the single unit of work; then `sprint2-checks.yml` and the abi-check job should be rewritten to invoke it (or its sub-commands) so the YAML degrades into a thin trigger wrapper. The existing divergence proves the NixCI point already: the only local build script in the tree, `llm-wiki/_scratch/build.cmd`, disables `LEGENDS_WERROR` while CI builds do not ([[Local Dev Loop]]) — exactly the "local passes / remote fails: untrustworthy" cell. ^[from https://blog.nix-ci.com/post/2026-03-09_ci-should-fail-on-your-machine-first (retrieved 2026-06-10)]

### 2. CMake workflow presets are the native mechanism for the build/test legs — but only those legs

Workflow presets bundle configure→build→test into one named command: "steps — A required array of objects describing the steps of the workflow. The first step must be a configure preset, and all subsequent steps must be non-configure presets whose configurePreset field matches the starting configure preset," invoked as `cmake --workflow --preset <name>`. ^[from https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html (retrieved 2026-06-10)] They exist precisely for the parity problem — presets were added because "One problem that CMake users often face is sharing settings with other people for common ways to configure a project. This may be done to support CI builds." ^[from https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html (retrieved 2026-06-10)] The hard limitation: "Subsequent steps must be either build, test, or package" ^[from https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html (retrieved 2026-06-10)] — a workflow preset cannot run `scripts/check_*.py`, the ABI compile, or any arbitrary command, so it is the bottom layer of the preflight, not the whole preflight.

**Applicability to Project Legends:** `CMakePresets.json` is already at schema version 6, the exact version where "Workflow Presets were added" ^[from https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html (retrieved 2026-06-10)] (`CMakePresets.json:2`), and already has matching configure/build/test preset triples for `dev`, `ipc`, and `coverage` (`CMakePresets.json:8-218`) — adding a `workflowPresets` array is pure JSON, no version bump, no new tooling. One workflow preset per mandatory-tier configuration (`preflight-dev`, `preflight-ipc`, plus `release` build-only) collapses Local Dev Loop replication step 1 from six manual commands to two or three. Two prerequisites: (a) CI must switch from raw `-D` flags (`ci.yml:64-71`, `sprint2-checks.yml:99-105`) to `cmake --workflow --preset` so the preset *is* the shared definition rather than a third copy of the flags; (b) per-OS reachability should be encoded with `condition` — "this can be used to disable a preset on platforms other than Windows" ^[from https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html (retrieved 2026-06-10)] — because today the `asan`/`tsan` presets hard-code `clang-18` and libc++ (`CMakePresets.json:63-67, 82-86`) and the `coverage` preset hard-codes `gcc-13` (`CMakePresets.json:110-112`), all of which fail opaquely on a Windows/MSVC machine. Developer-specific variations (a Windows dev's vcvars path, a different clang) belong in the untracked `CMakeUserPresets.json`: "CMakePresets.json may be checked into a version control system, and CMakeUserPresets.json should NOT be checked in." ^[from https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html (retrieved 2026-06-10)]

The honest scope note: a Windows developer can never mirror the full 4-configuration tier (two of the four are Linux-toolchain builds), and CI runners are weaker than dev machines anyway — "GitHub Actions' runners currently offer only 4 vCPUs and 16 GB RAM, considerably less than a typical developer machine" ^[from https://blog.nix-ci.com/post/2026-03-09_ci-should-fail-on-your-machine-first (retrieved 2026-06-10)] — so the preflight contract should be "every gate that can run on this OS," with the residue (MSVC for Linux devs, sanitizers for Windows devs) left to remote CI by design.

### 3. Hook manager vs plain git hooks: the current `.githooks` approach is the weakest option on a Windows+Linux team

Both major hook managers solve the same two defects of the current setup — single-check coverage and undocumented opt-in installation. pre-commit is "a multi-language package manager for pre-commit hooks" whose repository-local hook type exists for exactly this repo's case: "Repository-local hooks are useful when: The scripts are tightly coupled to the repository and it makes sense to distribute the hook scripts with the repository." ^[from https://pre-commit.com/ (retrieved 2026-06-10)] Lefthook is "a single dependency-free binary which can work in any environment" that "installs the configured hooks into .git/hooks/" from a committed `lefthook.yml`, runs jobs in parallel, and installs on Windows via winget or scoop. ^[from https://lefthook.dev/ (retrieved 2026-06-10)] ^[from https://raw.githubusercontent.com/evilmartians/lefthook/master/README.md (retrieved 2026-06-10)]

> [!conflict]
> Which manager — or none — is disputed territory. pre-commit's model assumes hooks may "manage the installation and execution of any hook written in any language" with isolated environments ^[from https://pre-commit.com/ (retrieved 2026-06-10)], which is overhead when all eleven checks are plain stdlib-ish Python scripts already in `scripts/`; it also requires a working Python before the hook runs (circular for a Python-toolchain repo only in theory — Python is already a hard dev dependency here). Lefthook is dependency-free and parallel ^[from https://raw.githubusercontent.com/evilmartians/lefthook/master/README.md (retrieved 2026-06-10)] but adds a third config dialect (YAML) beside CMakePresets.json and the workflows. The plain-git-hooks position (keep `core.hooksPath`) has the lowest footprint but is what produced the current state: a bash-only hook (`.githooks/pre-commit:1`) that depends on Git-for-Windows' bundled sh and a `python` (not `py`) launcher being on PATH, covers one check of eleven, and whose installation instruction lives in a comment inside the hook itself (`.githooks/pre-commit:3`). No source defends that combination; the disagreement is only about which replacement. Given the checks are already Python and CI already pip-installs the one dependency (`sprint2-checks.yml:41-42`), pre-commit with `repo: local` hooks is the smallest delta; Lefthook is preferable if parallel multi-config builds in the pre-push tier are wanted.

**Applicability to Project Legends:** either manager turns the eleven `scripts/check_*.py` into committed, named, glob-filtered hook entries — e.g. pre-commit `repo: local` entries with `language: system`, `entry: python scripts/check_includes.py --path .`, `types: [c++]`-style filters, or lefthook jobs with `glob:` filters and `{staged_files}` templating ^[from https://pre-commit.com/ (retrieved 2026-06-10)] ^[from https://raw.githubusercontent.com/evilmartians/lefthook/master/README.md (retrieved 2026-06-10)]. Both also give the hook/CI parity loop for free: "adding pre-commit run --all-files as a CI step will ensure everything stays in tip-top shape" ^[from https://pre-commit.com/ (retrieved 2026-06-10)] — i.e. the sprint2 script steps collapse into one step that runs the identical config developers run, closing the gap where the hook checks one thing and CI checks ten ([[Quality Gate Scripts & Hooks]]). Lefthook's `lefthook-local.yml` additionally gives per-developer skips without forking the committed config. ^[from https://raw.githubusercontent.com/evilmartians/lefthook/master/README.md (retrieved 2026-06-10)]

### 4. Tier the preflight: fast staged-file hooks at commit, one-configuration preflight at push, full mirror on demand

The sources converge on three speeds. Commit-time hooks are for "identifying simple issues before submission to code review" and by default run "only on the changed files" ^[from https://pre-commit.com/ (retrieved 2026-06-10)]; within any test entry point, cheap checks go first — "Linting ... tend[s] to run faster than tests, so put them towards the beginning of a script/test so it fails faster." ^[from https://github.com/github/scripts-to-rule-them-all (retrieved 2026-06-10)] pre-commit's stage system is the explicit mechanism: hooks declare `stages: [pre-commit, pre-merge-commit, pre-push, manual]`, installation targets are chosen with `default_install_hook_types: [pre-commit, pre-push]`, and "the manual stage ... is a special stage which will not be automatically triggered by any git hook — this is useful if you want to add a tool which is not automatically run, but is run on demand using pre-commit run --hook-stage manual." ^[from https://pre-commit.com/ (retrieved 2026-06-10)] Lefthook expresses the same with hook groups plus arbitrary named task groups run via `lefthook run <name>`. ^[from https://raw.githubusercontent.com/evilmartians/lefthook/master/README.md (retrieved 2026-06-10)]

> [!conflict]
> Tiering is in tension with the parity principle. NixCI is categorical that "it is important that the local checks are the same as the remote checks" — a curated fast subset is precisely a divergence, and the context-switching analysis implies no commit-time hook suite that includes builds can be fast enough anyway. ^[from https://blog.nix-ci.com/post/2026-03-09_ci-should-fail-on-your-machine-first (retrieved 2026-06-10)] The hook-manager sources instead institutionalize subsetting (staged-files filtering, stage lists). ^[from https://pre-commit.com/ (retrieved 2026-06-10)] The reconciliation that satisfies both: tiers must be *prefixes of the same command set*, not different commands — the commit tier runs some of the preflight's gates on fewer files, never variant flags or variant scripts; the on-demand tier and the CI mandatory tier are byte-identical invocations. The `build.cmd` `LEGENDS_WERROR=OFF` deviation is the canonical violation to ban.

**Applicability to Project Legends:** concretely — **commit tier** (seconds): `check_includes.py`, `check_conflict_markers.py`, `check_case_collisions.py` on staged files; **push tier** (a few minutes): all nine sprint2 script gates + the ABI compile (`gcc -std=c11 -Werror` on `include/legends/legends_embed.h`, mirroring `ci.yml:414-419`; on Windows, `cl /TC` or clang is the reachable approximation — flag this asymmetry in the preflight output rather than skipping silently) + `cmake --workflow --preset preflight-dev`; **on-demand `preflight` target** (minutes, parallelizable): push tier plus the remaining OS-reachable workflow presets (`preflight-ipc`; `release`; sanitizers on Linux). The 4-configuration matrix is CPU-bound, not serial — Lefthook's `parallel: true` ^[from https://raw.githubusercontent.com/evilmartians/lefthook/master/README.md (retrieved 2026-06-10)] or a task-runner equivalent keeps "minutes" honest on an 8+-core dev machine that out-resources the 4-vCPU CI runner. ^[from https://blog.nix-ci.com/post/2026-03-09_ci-should-fail-on-your-machine-first (retrieved 2026-06-10)]

### 5. Windows is a first-class constraint: pick tooling whose Windows story is explicit

Each candidate layer has a specific Windows behavior that must be checked, not assumed. just: "Linux, macOS, Windows, and other reasonable unixes are supported with no additional dependencies. (Although if your system doesn't have an sh, you'll need to choose a different shell.)" — and crucially "just uses sh on Windows by default," fixed with `set windows-shell := ["powershell.exe", "-NoLogo", "-Command"]`, where "set windows-shell has higher precedence than set shell, you can use set windows-shell to pick a shell on Windows, and set shell to pick a shell for all other platforms." ^[from https://just.systems/man/en/configuring-the-shell.html (retrieved 2026-06-10)] ^[from https://just.systems/man/en/settings.html (retrieved 2026-06-10)] Lefthook ships native Windows binaries via "winget ... scoop." ^[from https://lefthook.dev/ (retrieved 2026-06-10)] pre-commit runs on Windows (its own docs cache `%USERPROFILE%\.cache\pre-commit` in the AppVeyor example). ^[from https://pre-commit.com/ (retrieved 2026-06-10)] CMake presets are inherently cross-platform, with `condition` for per-OS preset gating. ^[from https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html (retrieved 2026-06-10)]

**Applicability to Project Legends:** the Windows-specific traps in this repo: (a) MSVC's environment — the Ninja `dev` preset only works from a vcvars shell (the `llm-wiki/_scratch/build.cmd:2` sources `vcvars64.bat` before anything else); a preflight entry point on Windows must either locate vcvars itself (vswhere) or document the Developer PowerShell requirement in `CONTRIBUTING.md`, because `cmake --workflow --preset preflight-dev` from a plain shell fails at configure; (b) the `default` preset's generator is "MinGW Makefiles" (`CMakePresets.json:12`) while `default-ninja` is the real base — preset naming should make the MSVC+Ninja path the obvious one; (c) shebang-style hooks: the current bash hook works only because Git-for-Windows bundles sh — any non-bash logic added to it breaks; both hook managers eliminate this by making the `.git/hooks/` shim trivial ("Hook is a simple script that calls lefthook run {hook-name}"). ^[from https://lefthook.dev/ (retrieved 2026-06-10)] If a task runner is chosen over a bare Python script, prefer recipes written as Python-shebang recipes or `set windows-shell` to PowerShell — never sh-isms — since recipes "can be written in arbitrary languages, like Python." ^[from https://just.systems/man/en/introduction.html (retrieved 2026-06-10)]

### 6. Document and auto-install the hooks; verify installation rather than trusting it

The pattern every source shares: the hook config is committed, the install command is one well-known line, and something verifies it happened. pre-commit: "run pre-commit install to set up the git hook scripts," with `default_install_hook_types` controlling which hook types one install command wires. ^[from https://pre-commit.com/ (retrieved 2026-06-10)] Lefthook: "Configure lefthook.yml, run lefthook install" — plus config options for enforcement (`assert_lefthook_installed`) and CI validation (`lefthook validate`, `lefthook check-install`). ^[from https://lefthook.dev/ (retrieved 2026-06-10)] Scripts-to-rule-them-all locates install steps in `script/bootstrap`, "used solely for fulfilling dependencies of the project," so a fresh clone reaches working state with one documented command. ^[from https://github.com/github/scripts-to-rule-them-all (retrieved 2026-06-10)] And because installation can never be guaranteed, the same checks run remotely: `pre-commit run --all-files` as a CI step makes the hook suite un-bypassable. ^[from https://pre-commit.com/ (retrieved 2026-06-10)]

**Applicability to Project Legends:** today the install instruction (`git config core.hooksPath .githooks`) exists only as a comment at `.githooks/pre-commit:3`, and `CONTRIBUTING.md` contains no mention of hooks or any `scripts/check_*.py` ([[Local Dev Loop]]). Minimum fix regardless of tooling choice: a "Setup" section in `CONTRIBUTING.md` (clone → bootstrap → hook install → `preflight`), and the preflight target itself should check hook installation and warn (the cheapest `assert_lefthook_installed` equivalent: compare `git config core.hooksPath` / probe `.git/hooks/pre-commit` and print the install one-liner). The bootstrap step also owns the pip dependency (`pyyaml`) that `check_capability_matrix.py` needs and CI installs at `sprint2-checks.yml:41-42` but no local doc mentions.

## Most applicable practices (ranked)

1. **Single committed entry point, consumed by CI** (practices 1 + 2): add `workflowPresets` to `CMakePresets.json` (already schema v6) for the build/test legs and a `scripts/preflight.py` that runs script gates + ABI check + OS-reachable workflow presets; rewire `ci.yml`/`sprint2-checks.yml` steps to call the same commands so divergence is structurally impossible.
2. **Replace the one-check opt-in hook with a managed, tiered hook config** (practices 3 + 4): pre-commit `repo: local` (or lefthook) covering all eleven scripts — staged-file subset at commit, script gates + one workflow preset at push, full preflight on demand; same commands at every tier, only scope varies.
3. **Document setup and verify hook installation** (practice 6): CONTRIBUTING.md setup section with the install one-liner, preflight warns when hooks aren't installed, and CI runs the identical hook config so opt-out only moves the failure later, never around it.
