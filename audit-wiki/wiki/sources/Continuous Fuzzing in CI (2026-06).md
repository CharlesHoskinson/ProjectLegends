# Continuous Fuzzing in CI (2026-06)

## Summary

Research synthesis on running the five libFuzzer targets (`tests/fuzz/fuzz_engine_load_state.cpp`, `fuzz_engine_memory_blob.cpp`, `fuzz_legends_load_state.cpp`, `fuzz_input_injection.cpp`, `fuzz_config_parser.cpp`) as effective continuous fuzzing rather than a ritual. Raw notes with full quoted passages: `raw/research/continuous-fuzzing-ci.md`. Six sources, all retrieved 2026-06-10: ClusterFuzzLite running-modes and GitHub Actions docs, OSS-Fuzz CIFuzz, acceptance + corpora, and ideal-integration docs, and the LLVM libFuzzer manual.

Current repo state this applies to: the `fuzz` job (ci.yml:478-578) builds all targets with clang-18 + ASan (ci.yml:497-509), regenerates the seed corpus from `generate_fuzz_corpus` into `build/tests/fuzz/corpus` on every run (ci.yml:511-512), runs a 30s-per-target smoke on PRs and master pushes (ci.yml:515-538) and 60s-per-target steps otherwise (ci.yml:540-578). No corpus directory is committed under `tests/fuzz/`, no `actions/cache` or `upload-artifact` step exists anywhere in the job, and `fuzz_input_injection` runs with no corpus directory at all (ci.yml:530-532). The lane failed 6 of 6 sampled executions ([[CI Run History (2026-06)]]). The PR smoke step was dead code at audit HEAD ef11f20 — the job-level `if` excluded pull_request ([[Build & CI Audit (2026-06)]], finding on ci.yml:474) — and was restored by commit ee8a9e2 ("ci: restore sanitizer and fuzz gates"); the current `if` (ci.yml:482-487) includes pull_request. Save-state deserialization is the documented attack surface with a prior heap-overflow finding ([[Memory Safety Audit (2026-06)]], [[Security Audit (2026-06)]]).

## Applicable practices

### 1. Persist and grow the corpus across runs; stop regenerating from scratch

Coverage-guided fuzzing is cumulative by design: "If a mutation triggers execution of a previously-uncovered path in the code under test, then that mutation is saved to the corpus for future variations," and new interesting inputs "will be written back to the first corpus directory." ^[from https://llvm.org/docs/LibFuzzer.html (retrieved 2026-06-10)] Batch fuzzing's second purpose is exactly this accumulation: "It builds a corpus for each of your fuzz targets, leading to more code coverage and better bug discovery. ... The corpus is saved using your CI system's feature for storing files." ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/ (retrieved 2026-06-10)] A growing corpus needs periodic pruning — "Corpus pruning should be considered mandatory when you are using batch fuzzing" ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/ (retrieved 2026-06-10)] — which libFuzzer implements natively: `-merge=1 NEW_CORPUS_DIR FULL_CORPUS_DIR` minimizes "while still preserving the full coverage." ^[from https://llvm.org/docs/LibFuzzer.html (retrieved 2026-06-10)]

> [!conflict]
> Where the persistent corpus should live is genuinely disputed. OSS-Fuzz's ideal-integration guidance puts the seed corpus "available in revision control (it can be the same as or different from the source code)," regularly extended with bug-triggering inputs. ^[from https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/ (retrieved 2026-06-10)] ClusterFuzzLite on GitHub recommends a *separate* git storage repo ("An empty repository for this is sufficient. The corpus have to be uploaded ... under `/corpus/<fuzz_target>/`"), falling back to GitHub Actions artifacts when none is configured. ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/github-actions/ (retrieved 2026-06-10)] Hosted OSS-Fuzz keeps corpora out of git entirely, "stored on Google Cloud Storage" with "daily zipped backups." ^[from https://google.github.io/oss-fuzz/advanced-topics/corpora/ (retrieved 2026-06-10)] The reconciliation: a small curated *seed* corpus (valid save-states, configs, past crash reproducers) belongs in the main repo; the large *generated* corpus belongs in external storage (storage repo, artifacts, or `actions/cache`) where its churn doesn't pollute history.

**Applicability to Project Legends:** the "Generate seed corpus" step (ci.yml:511-512) rebuilds the same generator-produced inputs every run and the run's discoveries evaporate with the runner, so every execution re-explores the same shallow frontier — the worst configuration for a format as stateful as save-state deserialization. Minimal in-repo fix without adopting ClusterFuzzLite: wrap `build/tests/fuzz/corpus` per target in `actions/cache` (a corpus key per fuzz target, `restore-keys` falling back to the latest), keep `generate_fuzz_corpus` as the cold-start seeder rather than the every-run overwriter, and add a nightly `-merge=1` prune step so the cache doesn't accrete redundant entries. Additionally commit a small `tests/fuzz/corpus/<target>/` seed set — the CMakeLists already copies `${CMAKE_CURRENT_SOURCE_DIR}/corpus` into the build tree if it exists (tests/fuzz/CMakeLists.txt), so the hook is built and currently dead. The prior heap-overflow reproducer belongs there.

### 2. Treat the PR budget as smoke-only, or fund it to documented floors

Both Google systems put PR fuzzing at an order of magnitude above the current budget: ClusterFuzzLite code-change mode "defaults to fuzzing for 10 minutes" ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/ (retrieved 2026-06-10)] and CIFuzz instructs "This value should be at minimum 600 seconds and scale with project size." ^[from https://google.github.io/oss-fuzz/getting-started/continuous-integration/ (retrieved 2026-06-10)] The budget is made affordable by selection, not truncation: with coverage data, "code change fuzzing will ... determine which fuzzers are affected by a code change. If code change fuzzing can determine which fuzzers are affected, it will run only those fuzzers" ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/ (retrieved 2026-06-10)]; CIFuzz likewise "only runs the fuzzers affected by a pull request/commit," otherwise it divides the allotted time among all targets. ^[from https://google.github.io/oss-fuzz/getting-started/continuous-integration/ (retrieved 2026-06-10)] Path-scoped triggers are the documented coarse version of the same idea (CIFuzz example triggers only on `**.c/.cc/.cpp/.cxx/.h` changes). ^[from https://google.github.io/oss-fuzz/getting-started/continuous-integration/ (retrieved 2026-06-10)]

> [!conflict]
> Whether a 30-60s run has *any* value depends on what it runs. As fuzzing, it is below every documented floor — 600s minimum per CIFuzz ^[from https://google.github.io/oss-fuzz/getting-started/continuous-integration/ (retrieved 2026-06-10)] — and starting from a regenerated corpus it cannot reach deep states. But libFuzzer documents a non-fuzzing mode that is cheap and meaningful at this budget: "If a list of files (rather than directories) are passed to the fuzzer program, then it will re-run those files as test inputs but will not perform any fuzzing. In this mode the fuzzer binary can be used as a regression test (e.g. on a continuous integration system)" ^[from https://llvm.org/docs/LibFuzzer.html (retrieved 2026-06-10)]; OSS-Fuzz's ideal integration makes the same separation — "Fuzz targets should be regularly tested (not necessarily fuzzed!) as a part of the project's regression testing process," with sanitizers. ^[from https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/ (retrieved 2026-06-10)] The honest PR design is replay-the-corpus-and-reproducers (deterministic, fast, catches regressions of fixed bugs), with real fuzzing time moved to the scheduled lane.

**Applicability to Project Legends:** the 30s smoke (ci.yml:515-538) is fuzzing theater on a from-scratch corpus, while occupying a 15-minute-timeout job slot. Convert it to corpus + reproducer replay (pass files/seed corpus to each `fuzz_*` binary, ASan still active) so PR red means "a known input broke," and let the 03:00 cron (ci.yml:25-27) own actual exploration at 600s+ per target — the existing 60s nightly steps (ci.yml:540-578) are also below floor for a five-target project whose main attack surface is a structured binary format. The current uniform `-max_total_time` split also ignores affected-target selection; even without ClusterFuzzLite, a `paths` filter so the lane's fuzz portion runs only when `src/`, `engine/`, or `tests/fuzz/` change is the coarse equivalent.

### 3. Separate pre-existing bugs from new bugs with a continuous-build baseline

A PR fuzz lane is only a usable gate if it reports *novel* crashes. CIFuzz's filter is two conditions: "The crash is reproducible (on the PR/commit build). The crash does not occur on older OSS-Fuzz builds. (If the crash does occur on older builds, then it was not introduced by the PR/commit being tested.)" ^[from https://google.github.io/oss-fuzz/getting-started/continuous-integration/ (retrieved 2026-06-10)] ClusterFuzzLite implements the baseline as the continuous-builds task — "if the cause of the crash was pre-existing, the crash is not reported by code change fuzzing. If code change fuzzing is run without the continuous builds task, all crashes will be reported" ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/ (retrieved 2026-06-10)] — with the batch lane as the place where the pre-existing backlog is surfaced: "batch fuzzing reports all crashes, not just 'new' ones," and "when you first use ClusterFuzzLite, code change fuzzing will not report the bugs that already exist in your codebase, while batch fuzzing will." ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/ (retrieved 2026-06-10)] Unreproducible crashes are suppressed by default (`report-unreproducible-crashes: false`). ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/ (retrieved 2026-06-10)]

**Applicability to Project Legends:** the hand-rolled job has no baseline concept: any crash, pre-existing or new, fails whichever event triggered the run, which is consistent with a lane that failed every sampled execution ([[CI Run History (2026-06)]]) and with the documented response of demoting the gate rather than triaging it ([[Quality Gate Demotion (2026-06-08)]]). With a known unfixed-crash class in save-state deserialization, a PR author touching unrelated code can draw a red X from someone else's bug — exactly the "unrelated failures" the continuous-builds task exists to remove. ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/github-actions/ (retrieved 2026-06-10)] Either adopt ClusterFuzzLite's build/batch/PR mode split, or fake the baseline cheaply in-repo: nightly lane reports all crashes to issues (not to the PR gate), PR lane fails only on inputs not already known to crash master (replay practice 2 gives this almost for free, since the replay set contains only vetted inputs).

### 4. Capture, minimize, and recycle crash artifacts

libFuzzer writes the triggering input to disk on every crash ("typically as crash-<sha1>, leak-<sha1>, or timeout-<sha1>"), at a location controlled by `-artifact_prefix` / `-exact_artifact_path`. ^[from https://llvm.org/docs/LibFuzzer.html (retrieved 2026-06-10)] Every CI integration treats uploading that file as mandatory plumbing: ClusterFuzzLite — "When the fuzzer crashes the input file that causes the crash is uploaded as an artifact" ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/github-actions/ (retrieved 2026-06-10)]; CIFuzz's reference workflow has an explicit `Upload Crash` step (`actions/upload-artifact@v4` on `failure()`, `path: ./out/artifacts`) plus SARIF upload into GitHub code scanning. ^[from https://google.github.io/oss-fuzz/getting-started/continuous-integration/ (retrieved 2026-06-10)] Triage is then minimize-and-recycle: libFuzzer's `-minimize_crash=1` shrinks the reproducer ("Use with -runs=N or -max_total_time=N to limit the number of attempts") ^[from https://llvm.org/docs/LibFuzzer.html (retrieved 2026-06-10)], ClusterFuzzLite exposes the same as `minimize-crashes` ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/ (retrieved 2026-06-10)], and the minimized input flows back into the version-controlled corpus, which "should be regularly extended with the inputs that (used to) trigger bugs." ^[from https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/ (retrieved 2026-06-10)] For long batch runs, fork mode keeps one crash from ending the session: `-fork=N` "enables oom-, timeout-, and crash-resistant fuzzing with separate processes," saving reproducers and continuing. ^[from https://llvm.org/docs/LibFuzzer.html (retrieved 2026-06-10)]

**Applicability to Project Legends:** the fuzz job (ci.yml:478-578) has no `upload-artifact` step, so when a target crashes, the `crash-<sha1>` file is written to the runner's working directory and destroyed with it — a 6/6-failing lane has therefore been discarding its reproducers every night, which is why the lane produces red checkmarks instead of bug reports. Minimum fix: set `-artifact_prefix=artifacts/` on every invocation and add an `actions/upload-artifact` step with `if: failure()`. The triage loop then closes through practice 1's committed corpus: minimize the reproducer locally (`-minimize_crash=1`), commit it under `tests/fuzz/corpus/<target>/`, and the PR replay step regression-tests it forever. Note also libFuzzer's defaults interact with the targets' parameters: `fuzz_engine_memory_blob` runs with `-max_len=1048576` (ci.yml:524-528) against a default `-rss_limit_mb=2048` and default 1200s `-timeout` that exceeds the step's own 30-60s budget — OOM/slow-input failures will look like crashes in the log unless the artifact is captured and classified. ^[from https://llvm.org/docs/LibFuzzer.html (retrieved 2026-06-10)]

### 5. ClusterFuzzLite is the eligible managed option; hosted OSS-Fuzz is not; the hand-rolled job is the fallback, not the goal

Hosted OSS-Fuzz has an explicit admission bar: "an open-source project must have a significant user base and/or be critical to the global IT infrastructure," with a Google-account-linked committer as contact. ^[from https://google.github.io/oss-fuzz/getting-started/accepting-new-projects/ (retrieved 2026-06-10)] CIFuzz additionally requires "Your project must be integrated with OSS-Fuzz." ^[from https://google.github.io/oss-fuzz/getting-started/continuous-integration/ (retrieved 2026-06-10)] The documented path for everyone else is ClusterFuzzLite: "Non-OSS-Fuzz users can use CIFuzz with additional features through ClusterFuzzLite" ^[from https://google.github.io/oss-fuzz/getting-started/continuous-integration/ (retrieved 2026-06-10)] — it runs natively on GitHub Actions (also GitLab, Cloud Build, Prow), supports C++ with libFuzzer plus ASan/UBSan/MSan, works on private repos with the default GitHub token, and packages all four lanes (PR code-change, scheduled batch, prune, coverage) as copy-in workflow files. ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/github-actions/ (retrieved 2026-06-10)] Its cost is the OSS-Fuzz-style build integration (a `.clusterfuzzlite/` Dockerfile + build script producing targets linked against `$LIB_FUZZING_ENGINE`), and a quota caveat: "If your builds are large they may exceed the free GitHub actions quotas. In this case it's recommended to not enable continuous builds." ^[from https://google.github.io/clusterfuzzlite/running-clusterfuzzlite/github-actions/ (retrieved 2026-06-10)]

**Applicability to Project Legends:** a GPL-2.0 DOSBox-X-derived embeddable emulation framework on GitHub does not clear the OSS-Fuzz "significant user base / critical infrastructure" bar today, so hosted OSS-Fuzz and CIFuzz are out; ClusterFuzzLite is squarely in scope and supplies, as configuration, everything practices 1-4 build by hand: storage-repo corpus persistence, 600s code-change fuzzing scoped to affected targets, continuous-build novelty filtering, crash artifact upload, prune and coverage crons. The five targets already use the `LLVMFuzzerTestOneInput` ABI (tests/fuzz/*.cpp), so build integration is a Dockerfile + a build.sh that re-expresses the existing CMake invocation (ci.yml:497-509, `-DENABLE_FUZZING=ON -DENABLE_ASAN=ON`). The realistic caveats: the OSS-Fuzz base container's pinned clang must cope with the C++23 codebase, and the engine build's size makes the continuous-builds artifact quota warning live. Decision shape: adopt ClusterFuzzLite for the PR + batch + prune lanes; keep a thin in-repo replay step (practice 2) as the deterministic required check, since required-check semantics for a matrixed external action are easier to reason about over a single replay job. The existing `fuzz` job then stops pretending to be both things at once.

### 6. Invest in seeds and dictionaries for the save-state and config formats

"The quality of the seed corpus has a huge impact on fuzzing efficiency; the higher the quality, the easier it is for the fuzzer to discover new code paths. The ideal corpus is a minimal set of inputs that provides maximal code coverage." ^[from https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/ (retrieved 2026-06-10)] libFuzzer is explicit that seedless operation degrades on structured inputs: it "will work without any initial seeds, but will be less efficient if the library under test accepts complex, structured inputs." ^[from https://llvm.org/docs/LibFuzzer.html (retrieved 2026-06-10)] For token-structured formats, "a simple dictionary of tokens used by the input language can have a dramatic impact on fuzzing efficiency. For example, when fuzzing an XML parser, a dictionary of XML tokens is helpful," maintained alongside the fuzz target. ^[from https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/ (retrieved 2026-06-10)]

**Applicability to Project Legends:** the generator (tests/fuzz/generate_corpus.cpp) is a good cold-start tool but produces only what its author already imagined; the two load_state targets fuzz a real serialization format whose headers, section tags, and length fields belong in (a) genuine save-states captured from the running emulator as committed seeds, and (b) a `.dict` file per format (save-state magic/section tokens; config keys for `fuzz_config_parser`) passed via `-dict=`. `fuzz_input_injection`'s smoke invocation has no corpus directory at all (ci.yml:530-532) — pure random bytes against an event-injection API every run. Given the prior heap overflow lived in save-state deserialization, seed + dictionary quality on `fuzz_engine_load_state` / `fuzz_legends_load_state` is the highest-leverage fuzzing investment in the repo; it is also what makes practice 2's short PR replay actually cover the attack surface.

## Most applicable practices (ranked)

1. **Persist the corpus and capture crash artifacts** (practices 1 + 4): `actions/cache` or a storage repo for `build/tests/fuzz/corpus`, `-artifact_prefix` + `upload-artifact` on failure, committed reproducer seeds under `tests/fuzz/corpus/` (the CMake copy hook already exists). Until artifacts survive the runner, the lane cannot produce bugs, only failures.
2. **Split the lane into a deterministic PR replay and a funded scheduled fuzz** (practices 2 + 3): PR step replays seeds + known reproducers (libFuzzer file-list mode, ASan on) as the required check; the nightly cron fuzzes 600s+ per target and is the only place new crashes surface — restoring the regression-vs-new-bug separation the 6/6-red gate lacks.
3. **Adopt ClusterFuzzLite for the managed version of all of the above** (practice 5): eligible (GitHub-hosted, no OSS-Fuzz admission bar), C++/libFuzzer/ASan-native, and replaces hand-rolled corpus storage, novelty filtering, pruning, and coverage-scoped PR fuzzing with four workflow files plus a build script.
