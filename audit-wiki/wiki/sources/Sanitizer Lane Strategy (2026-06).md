# Sanitizer Lane Strategy (2026-06)

External research synthesis: sanitizer lane placement (PR-gating vs nightly), allow-failure discipline, and TSan/MSan strategy for the Project Legends CI (C++23, gcc-13/clang-18, vendored DOSBox-X engine with legacy globals; `.github/workflows/ci.yml` `sanitizers` job, lines 328–373). Raw capture: `raw/research/sanitizer-lane-strategy.md`. All sources retrieved 2026-06-10.

Related: [[Verification Lanes (Sanitizers, Fuzz, Coverage, Determinism)]], [[CI Run History (2026-06)]], [[Build & CI Audit (2026-06)]], [[CI Workflows (GitHub Actions)]], [[Quality Gate Demotion (2026-06-08)]].

## Why this matters here

The `sanitizers` job in `.github/workflows/ci.yml` runs a four-way matrix (`address`, `undefined`, `thread`, `memory`) on every PR, push to `master`, schedule, and manual dispatch — pushes to `develop` get no sanitizer coverage. `thread` and `memory` carry `allow_failure: true` via `continue-on-error` (line 332), with in-file exit-plan comments deferring both to Sprint 7. Per [[CI Run History (2026-06)]], all four lanes failed every sampled execution — including the nominally enforced ASan and UBSan legs — so the lane currently produces no gating signal at all. The major-shop pattern is consistent: ASan (with UBSan) is the pre-commit sanitizer; TSan is brought to green via a curated suppression list and then enforced; MSan either gets a fully instrumented runtime or is not run.

## Applicable practices

### 1. ASan+UBSan are the PR-tier sanitizers; everything else earns its way in

Chromium wires ASan into its pre-commit trybots (`linux_chromium_asan_rel_ng`, `mac_chromium_asan_rel_ng`) and runs the persistent ASan/LSan bots on the Chromium Memory waterfall ^[from https://chromium.googlesource.com/chromium/src/+/HEAD/docs/asan.md (retrieved 2026-06-10)]. MSan bots, by contrast, run on the `chromium.memory.fyi` waterfall rather than in the default pre-commit set, with opt-in trybots (`linux_chromium_msan_rel_ng`) ^[from https://www.chromium.org/developers/testing/memorysanitizer/ (retrieved 2026-06-10)]. OSS-Fuzz encodes the same default at ecosystem scale: if a project doesn't specify sanitizers, it gets "a default list of supported sanitizers (currently 'address' and 'undefined')" — `memory` is opt-in only ^[from https://google.github.io/oss-fuzz/getting-started/new-project-guide/ (retrieved 2026-06-10)].

**Applicability to Project Legends:** the lane topology (ASan+UBSan enforced, TSan/MSan demoted) matches industry practice; the execution does not. The enforced legs fail every sampled run ^[from [[CI Run History (2026-06)]]], which means the PR tier is red-by-default and trains contributors to ignore it. First action is unglamorous: make the `address` and `undefined` legs (ci.yml lines 343–351) actually pass, before any TSan/MSan strategy work. Second: the job's `if:` (lines 334–338) covers `pull_request` and `push` to `master` but not `develop`; if `develop` is an integration branch, ASan/UBSan should run there too — Chromium's gating sanitizer runs both pre-commit and on the post-commit waterfall ^[from https://chromium.googlesource.com/chromium/src/+/HEAD/docs/asan.md (retrieved 2026-06-10)]. The `asan` preset in `CMakePresets.json` (lines 57–74) already combines `-fsanitize=address,undefined` into one build for local use; collapsing the two CI legs the same way would halve the PR-tier sanitizer compile cost without losing coverage.

### 2. Allow-failure should mean "evaluation period with a filing destination", not "ignore forever"

The only sanctioned run-but-don't-gate mode in the surveyed shops is explicitly temporary and explicitly tracked. OSS-Fuzz: a sanitizer can be marked `experimental: True` "to see what crashes it generates without filing them in the issue tracker", and a project that "does not build with a particular sanitizer configuration and you need some time to fix it" may override the defaults *temporarily* ^[from https://google.github.io/oss-fuzz/getting-started/new-project-guide/ (retrieved 2026-06-10)]. Firefox never ran TSan as a lane-level allow-failure at all: they used the suppression list "to temporarily ignore data races once we had them on file and ultimately bring up a TSan build of Firefox in CI that would automatically avoid further regressions", alongside an internal list of "all the most serious races that TSan detected (ones that had side-effects or could cause crashes)" ^[from https://hacks.mozilla.org/2021/04/eliminating-data-races-in-firefox-a-technical-report/ (retrieved 2026-06-10)] and a public `tsan` meta bug "maintained to keep track of all the bugs found with TSan" ^[from https://firefox-source-docs.mozilla.org/tools/sanitizer/tsan.html (retrieved 2026-06-10)]. The operational pattern: failures are converted into (a) filed bugs, (b) narrowly scoped suppressions referencing those bugs, and (c) a green, *enforced* lane that catches regressions — never a red lane that humans stop reading.

**Applicability to Project Legends:** the current `continue-on-error: ${{ matrix.allow_failure == true }}` (ci.yml line 332) is the anti-pattern: GitHub renders the job green-ish at the workflow level, no artifact distinguishes "same known races" from "new race introduced by this PR", and the lane has failed every sampled execution with nobody acting on it ^[from [[CI Run History (2026-06)]]]. The exit-plan comments in ci.yml (lines 352–357 and 362–367, "Sprint 7 tracks removing allow_failure...") are the right instinct — an allow-failure must carry an exit criterion — but the criterion lives in a YAML comment rather than in tracked issues plus a suppression file whose shrinkage is measurable. Concretely: replace lane-level `allow_failure` on TSan with a `tsan-suppressions.txt` checked into the repo (wired via `TSAN_OPTIONS=suppressions=...`), one entry per known race, each annotated with the tracking issue, then drop `allow_failure: true` so the lane gates on *new* races immediately. Sprint 7's exit work then becomes "delete suppression entries", which is reviewable, instead of "flip a CI flag", which is deferred indefinitely.

### 3. TSan on legacy globals: suppress-to-green beats defer-to-red

Firefox's engine had the same shape of problem — legacy C/C++ components, races on globals, components "explicitly designed to be single-threaded accidentally being used by multiple threads" ^[from https://hacks.mozilla.org/2021/04/eliminating-data-races-in-firefox-a-technical-report/ (retrieved 2026-06-10)]. The mechanics that made suppress-to-green workable:

- **Globals are the easy case for suppressions.** TSan matches suppression patterns against "global variable name (if present)" in addition to stack frames ^[from https://www.chromium.org/developers/testing/threadsanitizer-tsan-v2/ (retrieved 2026-06-10)], and Firefox's rule that a data-race suppression must name a frame from *each* of the two race stacks has exactly one exception: "when suppressing races on global variables[,] a single race entry with the name of the variable is sufficient" ^[from https://firefox-source-docs.mozilla.org/tools/sanitizer/tsan.html (retrieved 2026-06-10)]. So `race:g_active_instance` is a precise, one-line, reviewable suppression for the engine global named in ci.yml's own comments (lines 352–354).
- **Suppression hygiene is policy, not taste.** Chromium: "Good suppressions match a single race report (or a number of reports with a common root cause), but are unlikely to mask further races in other components. A suppression must be preceded by a comment ... with a crbug link" — and over-broad patterns (`race:New`, a whole test binary, a generic event-loop frame) are called out as bad ^[from https://www.chromium.org/developers/testing/threadsanitizer-tsan-v2/ (retrieved 2026-06-10)]. Firefox additionally distinguishes temporary from `permanent` suppressions in-line ^[from https://firefox-source-docs.mozilla.org/tools/sanitizer/tsan.html (retrieved 2026-06-10)].
- **Scoped instrumentation exists for whole-subsystem exclusion.** Chromium keeps a compile-time ignore list (`tools/memory/tsan_v2/ignores.txt`): a `fun:` entry stops TSan instrumenting that function ("effectively ignoring all memory accesses (but not synchronization)"), and `src:` ignores every function in a file ^[from https://www.chromium.org/developers/testing/threadsanitizer-tsan-v2/ (retrieved 2026-06-10)]. Tests that intentionally exercise racy paths are handled in code: "you should disable the test in the code under `#if defined(THREAD_SANITIZER)`" ^[from https://www.chromium.org/developers/testing/threadsanitizer-tsan-v2/ (retrieved 2026-06-10)].
- **Runtime suppressions require a symbolizer.** "TSan requires in-process symbolizing to work properly in the first place, as any kind of runtime suppressions will otherwise not work" — `llvm-symbolizer` must be on `PATH` or in `TSAN_SYMBOLIZER_PATH` ^[from https://firefox-source-docs.mozilla.org/tools/sanitizer/tsan.html (retrieved 2026-06-10)]. The sanitizers job installs only `clang-18 libc++-18-dev libc++abi-18-dev` (ci.yml lines 379–381); `llvm-18` (or the symlinked `llvm-symbolizer-18`) must be added or suppressions will silently not match.
- **Don't relitigate "benign".** Firefox adopted a "no data races" policy because races "are very easily misclassified as benign"; of the bugs they classified over a year, a third were called benign, yet most benign fixes were trivial (atomics conversions, code deletion) ^[from https://hacks.mozilla.org/2021/04/eliminating-data-races-in-firefox-a-technical-report/ (retrieved 2026-06-10)]. Their docs state the economics plainly: "we have decided to fix all data races wherever possible, since doing so is often cheaper than analyzing a race" ^[from https://firefox-source-docs.mozilla.org/tools/sanitizer/tsan.html (retrieved 2026-06-10)]. TSan itself is trustworthy here: properly deployed it has no false positives except fences, inline-assembly synchronization, uninstrumented code using builtin atomics, and the single-thread lock-inversion deadlock report ^[from https://firefox-source-docs.mozilla.org/tools/sanitizer/tsan.html (retrieved 2026-06-10)].

**Applicability to Project Legends:** the three known race families in the ci.yml comments (engine `g_active_instance`, `CrashBreadcrumb::add()`, intentional wrong-thread tests, lines 352–354) map one-to-one onto the toolkit: a `race:` global suppression, a function-frame suppression with issue link, and `#if defined(THREAD_SANITIZER)` (or a CTest label excluded in the `tsan` leg) respectively. The vendored engine tree is the candidate for `src:engine/*`-style compile-time ignores *only if* runtime suppressions prove too noisy — Chromium treats ignores as the coarser, second-choice tool since they hide accesses but keep synchronization. The `tsan` preset (CMakePresets.json lines 76–92) should grow the same `suppressions=` option so local runs and CI agree on the known-race set. Sprint 7's REQ-TH-004 fixes then retire suppression entries one by one with the lane already gating.

> [!conflict]
> Suppression-list posture differs between the two Mozilla sources. The deployment report presents the suppression list as the enabling mechanism for bringing TSan up on a legacy codebase, including "permanent suppressions for upstream issues that we couldn't address immediately" as a normal fix category ^[from https://hacks.mozilla.org/2021/04/eliminating-data-races-in-firefox-a-technical-report/ (retrieved 2026-06-10)]. The steady-state docs "strongly encourage you to not" suppress, reserving it for races whose fix has unreasonable cost, and warn that each suppressed race also slows the whole TSan build because it must be symbolized on every occurrence ^[from https://firefox-source-docs.mozilla.org/tools/sanitizer/tsan.html (retrieved 2026-06-10)]. Resolution for this repo: these are phases, not contradictions — bring-up phase (now, Sprints up to 7) suppresses liberally-but-narrowly with issue links; steady state (post-Sprint-7) treats any new suppression as exceptional. The vendored-engine upstream relationship (DOSBox-X) makes some `permanent`-class suppressions legitimate long-term residents, exactly like Firefox's upstream-issue category.

### 4. MSan: instrumented libc++ or nothing — and "nothing" is the defensible default

The Clang documentation is unambiguous: "MemorySanitizer requires that all program code is instrumented. This also includes any libraries that the program depends on, even libc. Failing to achieve this may result in false reports", and "Full MemorySanitizer instrumentation is very difficult to achieve" — the libc interceptors only cover C-library calls, which is why the reference deployment "bootstrap[ped] MemorySanitizer-instrumented Clang ... by linking it with self-built instrumented libc++" ^[from https://clang.llvm.org/docs/MemorySanitizer.html (retrieved 2026-06-10)]. OSS-Fuzz draws the operational conclusion: MSan is "supported and recommended, but is not enabled by default due to the likelihood of false positives from un-instrumented system dependencies. If you want to use 'memory,' please build all libraries your project needs using MemorySanitizer" ^[from https://google.github.io/oss-fuzz/getting-started/new-project-guide/ (retrieved 2026-06-10)]. Chromium keeps its MSan bots on the `chromium.memory.fyi` waterfall even though its MSan builds get prebuilt instrumented system libraries automatically ("MSan requires using Instrumented system libraries"; `use_prebuilt_instrumented_libraries` "is now the default if is_msan is set") ^[from https://www.chromium.org/developers/testing/memorysanitizer/ (retrieved 2026-06-10)].

**Applicability to Project Legends:** the `memory` matrix leg (ci.yml lines 359–373) links stock `libc++-18-dev` — every C++ object that crosses the standard library is unanalyzable, and the in-file comment correctly records that "test executables crash on startup". This leg is not allow-failure; it is no-information: it cannot regress and cannot improve, and it burns a 20-minute-timeout runner on every PR. The two honest options match the ci.yml Sprint 7 comment exactly: (a) build or fetch an MSan-instrumented libc++ (the `cmake -DLLVM_USE_SANITIZER=MemoryWithOrigins` runtimes build per the linked clang doc chain) and point the leg at it with `-stdlib=libc++ -L/path -Wl,-rpath,...`, accepting that *all* C++ dependencies of the test binaries need the same treatment; or (b) retire the leg now and re-introduce it later, nightly-only, if option (a) is ever funded. Given the vendored DOSBox-X engine and SDL dependency surface, the OSS-Fuzz default posture — ship address+undefined, treat memory as an opt-in for projects that have done the instrumentation work — supports (b). Removing a lane that cannot run is not a loss of coverage; uninitialized-read overlap also exists (weaker) via valgrind/memcheck-style nightly options if ever needed.

### 5. Nightly belongs to the expensive and the flaky-by-nature; PR tier must be hermetic

Firefox publishes TSan builds of mozilla-central "updated at least daily" as the canonical consumption channel ^[from https://firefox-source-docs.mozilla.org/tools/sanitizer/tsan.html (retrieved 2026-06-10)], and warns that "the TSan algorithm does not guarantee, that a race is detected 100% of the time. Intermittent failures with TSan are (to a certain degree) to be expected" ^[from https://firefox-source-docs.mozilla.org/tools/sanitizer/tsan.html (retrieved 2026-06-10)]. MSan's 3x slowdown and 2x memory cost ^[from https://clang.llvm.org/docs/MemorySanitizer.html (retrieved 2026-06-10)] put it in the same nightly-or-waterfall cost class, which is where Chromium keeps it (MSan bots on `chromium.memory.fyi` and other non-pre-commit waterfalls) ^[from https://www.chromium.org/developers/testing/memorysanitizer/ (retrieved 2026-06-10)]. Both TSan and MSan are Linux-only ^[from https://firefox-source-docs.mozilla.org/tools/sanitizer/tsan.html (retrieved 2026-06-10)] ^[from https://clang.llvm.org/docs/MemorySanitizer.html (retrieved 2026-06-10)], so neither can ever cover the Windows/macOS legs of this repo's matrix — another reason not to overweight them in the PR tier.

**Applicability to Project Legends:** TSan's inherent intermittency means that even after suppress-to-green, the lane will occasionally detect a pre-existing race only sometimes — each such event should produce a new suppression+issue pair, not a revert to allow-failure. The `schedule` trigger already present on the sanitizers job (ci.yml line 337) is the natural home for any heavier future variants (TSan with deeper trace history, MSan-with-instrumented-runtime, MSan origin tracking — which raises MSan's real-memory overhead from 2x over a native run to 3x ^[from https://clang.llvm.org/docs/MemorySanitizer.html (retrieved 2026-06-10)]); the PR tier should hold only the deterministic, green, enforced legs: ASan+UBSan now, TSan after suppression bring-up.

## Bottom line for the repo

Three moves, in order: (1) make the already-enforced ASan/UBSan legs green and extend them to `develop` pushes — they are the PR-tier sanitizers everywhere surveyed and they currently fail every sampled run; (2) convert TSan from lane-level `allow_failure` to an in-repo suppression file (issue-linked, globals suppressed by name, wrong-thread tests gated in code) and then enforce the lane, making Sprint 7 a suppression-burndown rather than a flag-flip; (3) retire the MSan leg until an instrumented libc++ exists, per the OSS-Fuzz default and Chromium's FYI-waterfall placement — a lane that crashes on startup by construction is spend without signal.
