# Vendored & License-Isolated Dependency CI (2026-06)

External research synthesis: best practice for CI that builds an MIT-intended framework around a vendored GPL-2.0 engine (~1M-line DOSBox-X fork in `engine/`), with GPL isolation implemented as an IPC process split (`src/legends_proxy` MIT ↔ `src/engine_host` GPL). Raw capture: `raw/research/vendored-license-isolation-ci.md`. All sources retrieved 2026-06-10.

Related: [[Docs & Licensing Audit (2026-06)]], [[Build & CI Audit (2026-06)]], [[Security Audit (2026-06)]].

## Why this matters here

The repo's license firewall is design-complete but enforcement-absent. `cmake/ModuleManifest.cmake` already declares the license-critical edges (`LEGENDS_DAG_legends_ipc ""`, `LEGENDS_DAG_legends_proxy "legends_ipc"`, `LEGENDS_DAG_legends_engine_host "legends_core;legends_ipc"`, with the comment "legends_proxy --> legends_ipc (MIT only)"), but `cmake/ModuleDAG.cmake`'s `legends_verify_all_dags()` verifies only `legends_core`, `legends_pal`, and `aibox_core` — the three license-critical targets are never checked, and `legends_detect_cycles()` hard-codes the same three-module list. `cmake/VerifyGPLIsolation.cmake` (a post-build linker-map symbol scan via `scripts/verify_gpl_isolation.py`, gated on `LEGENDS_USE_IPC`) is orphaned: no `include(VerifyGPLIsolation)` exists anywhere in the build, and even if included it degrades to `message(WARNING)` + `return()` when Python or the script is missing. The only scan job in `.github/workflows/ci.yml` (`dependency-scan`, REQ-SEC-028) runs osv-scanner for vulnerabilities only, fires only on `schedule`/`workflow_dispatch`, and is `continue-on-error` with `|| true` — it checks no licenses and gates nothing. The `linux-ipc` job builds the split but never asserts isolation. The prior audit graded licensing D for a bare-MIT root `LICENSE` over a GPL codebase; as of 2026-06-10 `LICENSE` has been rewritten into a component-license overview table (engine/ GPL; `src/legends_ipc/` + `include/legends_ipc/` MIT; `src/legends/`, `src/app/`, `src/pal/`, `src/engine_host/` GPL-2.0-or-later), and spot-checked sources in `src/legends_proxy/` and `src/legends_ipc/` carry `SPDX-License-Identifier: MIT` headers — but nothing in CI verifies any of this stays true.

## What process separation requires technically

The FSF's position (a legal opinion, theirs to make — the FAQ itself says where the line falls between two programs and one "is a legal question, which ultimately judges will decide") is that the criterion is both the mechanism of communication (exec, pipes, rpc, function calls in a shared address space) and the semantics (what information is interchanged) ^[from https://www.gnu.org/licenses/gpl-faq.html (retrieved 2026-06-10)]. Per the same FAQ: modules in one executable are "definitely combined in one program"; modules linked in a shared address space "almost surely" are; whereas "pipes, sockets and command-line arguments are communication mechanisms normally used between two separate programs", unless the semantics are "intimate enough, exchanging complex internal data structures" ^[from https://www.gnu.org/licenses/gpl-faq.html (retrieved 2026-06-10)]. For distributing GPL software alongside a proprietary (here: differently-licensed) system, the FSF requires that the programs "communicate at arms length" and — the form requirement — that distribution makes clear users have received "a free program plus another program, side by side" rather than GPL code described as "part of" the larger system ^[from https://www.gnu.org/licenses/gpl-faq.html (retrieved 2026-06-10)].

**Applicability to Project Legends:** the architecture in `docs/design/GPL2_PROCESS_ISOLATION_DESIGN.md` matches the favorable pattern on the control path — spawn `legends_engine_host` as a separate process, talk over a named pipe (Windows) / Unix domain socket (POSIX) with serialized request/response messages. The technical invariants CI must preserve are: (1) no GPL object ever linked into the MIT shell/proxy binary (same-executable test), (2) the IPC payloads stay serialized wire messages, not shared internal structures (semantics test), and (3) released artifacts present engine host and shell as two programs with their own licenses (form test, see manifests below).

> [!conflict]
> The FSF FAQ also states "Using shared memory to communicate with complex data structures is pretty much equivalent to dynamic linking" ^[from https://www.gnu.org/licenses/gpl-faq.html (retrieved 2026-06-10)], and the Legends design moves the framebuffer and audio ring over shared memory (`docs/design/GPL2_PROCESS_ISOLATION_DESIGN.md`, "Framebuffer (Shared Memory)", "Audio Ring (Shared Memory)"). The defensible reading is that pixel buffers and PCM rings are flat media payloads, not "complex internal data structures"; but the design doc nowhere argues this, and none of the fetched sources resolves how flat a shared-memory layout must be. This is a question for counsel, not for CI — what CI *can* enforce is that the shared-memory structs stay confined to the MIT `src/legends_ipc/` layer (both sides include the same MIT headers, so no GPL header crosses into the proxy) and that no engine-internal type appears in `include/legends_ipc/`.

## Applicable practices

### 1. Link-graph assertion over the license boundary (extend the DAG verifier)

The whole point of an arms-length split is that the boundary is a *link-time* property, so the first CI gate is a link-graph assertion: fail the build if the MIT-side targets acquire a GPL dependency. The FSF's same-executable criterion ("If the modules are included in the same executable file, they are definitely combined in one program") ^[from https://www.gnu.org/licenses/gpl-faq.html (retrieved 2026-06-10)] maps directly onto CMake's `LINK_LIBRARIES` graph.

**Applicability to Project Legends:** the machinery already exists — `cmake/ModuleDAG.cmake::legends_verify_dag()` FATAL_ERRORs on unauthorized internal links, and `cmake/ModuleManifest.cmake` already whitelists `legends_proxy → legends_ipc` only. The fix is to add `legends_verify_dag(legends_ipc)`, `legends_verify_dag(legends_proxy)`, and `legends_verify_dag(legends_engine_host)` to `legends_verify_all_dags()` (and the three targets to the `legends_detect_cycles()` module list), guarded by `if(TARGET ...)` as the existing calls are, since the targets only exist when `LEGENDS_USE_IPC=ON`. Note the existing `EXTERNAL_PATTERNS` whitelist in `ModuleDAG.cmake` (SDL, gsl, generator expressions) is generous; for the two MIT targets specifically, a stricter rule — no `engine`-prefixed or `legends_core` target ever, even transitively via `INTERFACE_LINK_LIBRARIES` — is warranted, because `get_target_property(... LINK_LIBRARIES)` sees only direct links.

### 2. Symbol-level scan of the shipped binary (resurrect the orphaned check)

A link-graph assertion checks intent in the build system; a symbol scan checks the artifact. The CMake-level declaration can drift from what the linker actually pulled in (object libraries, static archive members, LTO). `cmake/VerifyGPLIsolation.cmake` already implements the right shape — generate a linker map (`/MAP` on MSVC, `-Wl,-Map` on GCC/Clang) and scan it for GPL symbols post-build — and the comment in `CMakeLists.txt` line 423 states the invariant ("legends_proxy must NOT link any GPL-licensed targets").

**Applicability to Project Legends:** three defects to fix when wiring it in. (a) It is never included: add `include(VerifyGPLIsolation)` to the top-level `CMakeLists.txt` IPC branch. (b) It targets `project_legends` (the shell executable); the verification matters for every MIT-side artifact — shell *and* a standalone `legends_proxy` consumer build. (c) It fails open: the `message(WARNING)` + `return()` paths for missing Python/script must become `FATAL_ERROR` in CI (e.g. a `LEGENDS_REQUIRE_GPL_VERIFICATION` option the `linux-ipc` job sets), otherwise the gate silently vanishes on a misconfigured runner. The natural CI home is the existing `linux-ipc` job in `.github/workflows/ci.yml`, which already configures `LEGENDS_USE_IPC=ON` and "Verify IPC executables exist" — currently an existence check where an isolation check should be.

### 3. Per-file SPDX IDs on both sides of the firewall

SPDX short-form identifiers are the per-file mechanism that survives the file leaving the repo: "If your project only has license info in a top-level LICENSE.txt file, it can be harder for others to reuse your code. [...] An SPDX ID is located within each source code or documentation file, and follows that file into downstream projects" ^[from https://spdx.dev/learn/handling-license-info/ (retrieved 2026-06-10)]. They are machine-checkable ("as easy as running grep") and adoptable gradually ^[from https://spdx.dev/learn/handling-license-info/ (retrieved 2026-06-10)]. For GNU licenses the bare ID is wrong: "always use either the suffix `-only` or the suffix `-or-later`" ^[from https://spdx.dev/learn/handling-license-info/ (retrieved 2026-06-10)].

**Applicability to Project Legends:** spot-checks show the discipline largely exists (`src/legends_proxy/proxy_api.cpp` and all of `src/legends_ipc/*.cpp` carry `SPDX-License-Identifier: MIT`; the rewritten root `LICENSE` reports `GPL-2.0-or-later` tags on project GPL code, correctly suffixed). What is missing is the *lint*: a CI job that (a) fails if any file under `src/legends_proxy/`, `src/legends_ipc/`, `include/legends_ipc/` lacks an `SPDX-License-Identifier: MIT` line or carries a GPL expression, and (b) fails if MIT tags appear under `engine/` project-owned files that include GPL headers. Check (a) is a five-line grep gate implementable today, independent of full REUSE adoption.

### 4. REUSE compliance job; REUSE.toml for the vendored engine

The REUSE spec (v3.3, RFC 2119 terms) operationalizes per-file licensing: every Covered File MUST have Licensing Information; every license in use MUST have a License File in `LICENSES/` named by SPDX identifier; the project MUST NOT ship License Files for licenses it doesn't use ^[from https://reuse.software/spec-3.3/ (retrieved 2026-06-10)]. For exactly the vendored-tree problem, the spec provides `REUSE.toml`: "The intended use case of this method is large directories where including a comment header in each file [...] is impossible or undesirable", with per-`[[annotations]]` precedence (`closest`/`aggregate`/`override`) so bulk declarations and in-file headers compose ^[from https://reuse.software/spec-3.3/ (retrieved 2026-06-10)]. Git submodules are out of scope ("Each submodule [...] is understood as a separate Project") ^[from https://reuse.software/spec-3.3/ (retrieved 2026-06-10)] — relevant only if `engine/` is ever converted to a submodule. The enforcement side is turnkey: `reuse lint` as a pre-commit hook "will prevent your commit from going through if there was an error", and CI snippets exist for GitHub Actions (`fsfe/reuse-action@v6` on `[push, pull_request]`), GitLab, Drone/Woodpecker, Forgejo, and Travis ^[from https://reuse.software/dev/ (retrieved 2026-06-10)].

**Applicability to Project Legends:** a `REUSE.toml` at `engine/` declaring the DOSBox-X-derived tree (e.g. `precedence = "closest"` so upstream in-file headers win and the TOML only fills gaps) makes the 1M-line vendored mass compliant without touching upstream files — touching them would bloat every future vendor-drop diff. `LICENSES/MIT.txt`, `LICENSES/GPL-2.0-or-later.txt` (and `GPL-2.0-only` if the engine settles on -only), plus identifiers for gsl-lite/SDL3/zlib per `NOTICE`, complete the set; the existing root `COPYING`/`LICENSE` files are explicitly permitted and ignored by the tool ^[from https://reuse.software/spec-3.3/ (retrieved 2026-06-10)]. A `reuse lint` job in `ci.yml` on `[push, pull_request]` then subsumes the grep gate of practice 3 and pins the root-LICENSE-vs-source contradiction (the grade-D finding) permanently shut: the per-file tags become the checked ground truth and the prose `LICENSE` is just an ignored overview.

### 5. License scanning distinct from vulnerability scanning; policy-as-code on the boundary

Dependency *vulnerability* scanning and *license* scanning are different tools at different pipeline points. ORT's pipeline separates them explicitly: the Analyzer collects declared licenses from metadata; the Scanner detects licenses from file contents, "revealing envelope cases where the declared and detected licenses do not match" (e.g. a package declared MIT containing a BSD-3-Clause header); the Evaluator runs "custom policy rules along with custom license classifications [...] and returns a list of policy violations, e.g. to flag license findings"; the Advisor handles security advisories as a separate stage ^[from https://oss-review-toolkit.org/ort/docs/intro (retrieved 2026-06-10)] ^[from https://oss-review-toolkit.org/ort/docs/guides/license-handling (retrieved 2026-06-10)]. For vendored code whose true licensing diverges from a blanket declaration, ORT prefers narrow "license finding curations" over a blanket concluded license, because a blanket conclusion "blindly overrides everything" and new licenses introduced by a newer version "would go unnoticed" ^[from https://oss-review-toolkit.org/ort/docs/guides/license-handling (retrieved 2026-06-10)].

**Applicability to Project Legends:** the `dependency-scan` job in `.github/workflows/ci.yml` (osv-scanner over `cmake/dependencies.cmake` and `engine/`) is vulnerability-only and advisory-only (`schedule`/`workflow_dispatch` triggers, `|| true`, `continue-on-error: true`); no job anywhere checks licenses. The envelope-case concept maps exactly onto the grade-D finding: the repo itself was an envelope case — bare MIT "on the envelope", GPL inside. The minimal hardening is the REUSE job (practice 4) plus a boundary policy rule; the fuller version is an ORT (or scancode-based) job that scans `engine/` on vendor-drops and evaluates one rule: *no copyleft finding in any path linked into `legends_proxy`/`legends_ipc` artifacts*. Frequency can stay scheduled for the 1M-line engine scan (cost), but the rule evaluation on the MIT tree belongs on every PR. Keeping the vulnerability scan and the license scan as separate jobs mirrors the ORT stage split and keeps failure semantics distinct: license violations should block merge; new CVEs in vendored DOSBox-X code may legitimately be triaged asynchronously.

### 6. SBOM generation at build time, per artifact; validation as a release gate

Microsoft's engineering practice (the post is their account of their own pipeline): generate SBOMs "at build time [...] for all official builds", injected via existing CI/CD so generation is "on by default"; emit ISO/IEC 5962:2021 SPDX with the NTIA minimum fields (supplier, name, version, unique IDs, dependency relationships, author, timestamp — supplier/version/checksum/relationship made mandatory although optional in SPDX); store the SBOM *with the artifact* ("a new folder at the root of the build drop called _manifest"); sign it; and at release "validate the hashes of all files listed in the SBOM against the hashes of the build drop [...] If our SBOM validation tool detects a hash mismatch or incorrect signature, our SBOM validation tool will block the deployment" ^[from https://devblogs.microsoft.com/engineering-at-microsoft/generating-software-bills-of-materials-sboms-with-spdx-at-microsoft/ (retrieved 2026-06-10)]. ORT's Reporter covers the generation side for FOSS pipelines: "Generate CycloneDX, SPDX SBOMs, or custom FOSS attribution documentation", plus "Open Source notices or Bill-Of-Materials (BOMs)" as report outputs ^[from https://oss-review-toolkit.org/ort/docs/intro (retrieved 2026-06-10)]; the REUSE tool can also emit an SBOM from the per-file tags ("Eventually, you can generate a software bill of materials") ^[from https://reuse.software/dev/ (retrieved 2026-06-10)], and REUSE explicitly exempts `sbom.spdx.json` SPDX documents from per-file tagging ^[from https://reuse.software/spec-3.3/ (retrieved 2026-06-10)].

**Applicability to Project Legends:** the right insertion point is the `packaging` job in `.github/workflows/ci.yml` (tag-push only, three OSes) — after CPack assembles the drop, before artifact upload. Because the repo ships a *split* product, one SBOM per artifact is what makes the license firewall legible downstream: the proxy/shell package's SBOM lists MIT (+ zlib/MIT third-party) components only, and the engine-host package's SBOM lists the GPL engine with its DOSBox-X provenance (`NOTICE` already has the upstream URL and copyright line the SPDX Package fields need). A GPL package identifier appearing in the proxy artifact's SBOM is then a mechanically detectable release blocker — the SBOM becomes the third, artifact-level layer of the same invariant that practices 1–2 check at configure time and link time.

### 7. Per-artifact license manifests: the "form" half of compliance

The FSF's arms-length guidance has a distribution-form component easy to lose in CI plumbing: users must "clearly understand the free status of the GPL-covered software in the collection", receiving "a free program plus another program, side by side" rather than GPL code presented as "part of" the proprietary system ^[from https://www.gnu.org/licenses/gpl-faq.html (retrieved 2026-06-10)]. ORT names the deliverable — "Open Source notices" / attribution documents generated by the Reporter ^[from https://oss-review-toolkit.org/ort/docs/intro (retrieved 2026-06-10)] — and SPDX expressions give the unambiguous per-component vocabulary (`GPL-2.0-only` vs `GPL-2.0-or-later` vs ambiguous prose like "GPL v2.0") ^[from https://spdx.dev/learn/handling-license-info/ (retrieved 2026-06-10)].

**Applicability to Project Legends:** concretely, each release archive should carry: the engine-host binary's `COPYING` (GPL-2.0 text) and a written source offer or source archive alongside it; the shell/proxy's MIT text; and the per-artifact SBOM (practice 6). The packaging job currently has no notice-assembly step; `cmake/packaging.cmake` is the place to install license texts per component. The repo's open `-only`-vs-`-or-later` question (root `LICENSE` notes upstream DOSBox-X consistency with `GPL-2.0-or-later` but defers "a formal license declaration" to the maintainer) must be settled before the manifests can be generated truthfully — a release-blocking open item that the prior audit's grade-D finding already implies, and one the page sources cannot decide.

## Three highest-leverage moves

1. Extend `legends_verify_all_dags()` in `cmake/ModuleDAG.cmake` to the three IPC targets already declared in `cmake/ModuleManifest.cmake` — a several-line change activating an existing FATAL_ERROR gate on the exact MIT↔GPL boundary.
2. Wire `cmake/VerifyGPLIsolation.cmake` into the build (it is included nowhere today), make its missing-prerequisite paths fatal under CI, and run it in the existing `linux-ipc` job — turning "Verify IPC executables exist" into "verify the MIT binary contains no GPL symbols".
3. Add an `fsfe/reuse-action@v6` job on `[push, pull_request]` with a `REUSE.toml` covering `engine/` — per-file SPDX ground truth, mechanically enforced, ending the LICENSE-vs-source drift class for good ^[from https://reuse.software/dev/ (retrieved 2026-06-10)] ^[from https://reuse.software/spec-3.3/ (retrieved 2026-06-10)].
