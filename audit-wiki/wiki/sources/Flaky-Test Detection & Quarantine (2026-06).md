# Flaky-Test Detection & Quarantine (2026-06)

## Summary

External best-practice research on detecting and quarantining flaky tests, scoped to Project Legends' stack (C++23, GoogleTest, CTest, GitHub Actions). Eight sources: two Google Testing Blog posts (Micco 2016, Listfield 2017), Slack's auto-detection-and-suppression system, Spotify's flakiness tooling, GitHub's 18x flaky-build reduction, the ctest(1) manual, GoogleTest's advanced-topics docs, and a 2026 arXiv empirical study of rerun-derived flakiness in GitHub Actions. Raw extracts in `raw/research/flaky-test-quarantine.md`.

The repo-local motivation: commits 911692f ("Relax SDL backend startup event tests") and 8fdd4c6 ("Stabilize optional SDL backend CI") stabilized CI by deleting assertions rather than quarantining; [[CI Run History (2026-06)]] found rerun history invisible in the collected extract; no quarantine mechanism exists anywhere in the suite; and `pal-ci.yml`'s asan-lifecycle job already uses `--gtest_repeat=3` as an ad-hoc stability probe.

## Practices

### 1. Detection without rerun history: deterministic re-execution is the standard substitute

The canonical definition needs two outcomes on the same code: "a test that exhibits both a passing and a failing result with the same code" ^[from https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html (retrieved 2026-06-10)]. When CI rerun records are unavailable, the standard detectors generate the second outcome deliberately rather than waiting for it: GitHub's CI marks a failure flaky if a retry of the failed test passes within the same build ("This could be used on every build at minimal cost"), and separately compares builds run against the same root git tree hash ^[from https://github.blog/engineering/engineering-principles/reducing-flaky-builds-by-18x/ (retrieved 2026-06-10)]. The tool primitives for this on the Legends stack already exist: `ctest --repeat until-pass:<n>` ("Repeats tests if they fail for any reason ... useful in tolerating sporadic failures") distinguishes a flaky test from a failing one in a single CI invocation, while `ctest --repeat until-fail:<n>` ("Require each test to run <n> times without failing in order to pass ... useful in finding sporadic failures") is the burn-in mode ^[from https://cmake.org/cmake/help/latest/manual/ctest.1.html (retrieved 2026-06-10)]. At the GoogleTest binary level, `--gtest_repeat=N` with `--gtest_filter` repeats a suspect subset, and `--gtest_shuffle` with a logged `--gtest_random_seed` reproduces order-dependence deterministically ^[from https://raw.githubusercontent.com/google/googletest/main/docs/advanced.md (retrieved 2026-06-10)].

**Applicability to Project Legends:** detection does not require the missing rerun history. A nightly or weekly burn-in lane — `ctest --repeat until-fail:10` over the discovered tests in `CMakeLists.txt` (labels `unit`, `integration`, `ipc`, `toolchain`) plus `--gtest_shuffle` on `legends_unit_tests` — yields flakiness evidence on a fixed schedule. The asan-lifecycle step in `.github/workflows/pal-ci.yml` (lines 208–214, `--gtest_repeat=3` over `ContractGate_Lifecycle*`) is already a miniature until-fail probe; the practice generalizes it from one gtest filter to the whole suite via CTest. Conversely, a `--repeat until-pass:2` on the PR lane would convert "developer hits re-run on the whole workflow" into a per-test retry that also *records* which test needed the retry — the rerun signature the GitHub Actions API extract could not provide.

### 2. Attempt counts are a real but weak and expensive detection signal

Where rerun data exists, it is informative: in 1,960 GitHub Actions projects, 3.2% of builds were rerun and 67.73% of (intentional) rerun builds were flaky, with flaky tests the top failure category at 64.99% ^[from https://arxiv.org/html/2602.02307v1 (retrieved 2026-06-10)]. But the same study found 10,406 flaky builds needed more than one rerun to flip outcome (up to 20), rerun builds averaged 63x the waiting time of non-rerun builds, and "rerunning builds is not always an effective or efficient strategy" ^[from https://arxiv.org/html/2602.02307v1 (retrieved 2026-06-10)]. GitHub's own baseline (whole-build retry comparison plus single in-build retry) caught only 25% of flaky failures; raising that to 90% took three *differentiated* retries — same process, time-shifted, different host — which double as root-cause classification ^[from https://github.blog/engineering/engineering-principles/reducing-flaky-builds-by-18x/ (retrieved 2026-06-10)].

**Applicability to Project Legends:** attempt counts should be mined as a lagging indicator, not relied on as the detector. The study identified reruns from the `run_attempt` field and "collected all metadata and log files associated with every attempt to reconstruct the complete rerun sequence" ^[from https://arxiv.org/html/2602.02307v1 (retrieved 2026-06-10)] — so per-attempt data is recoverable from the Actions API if collected per attempt, and with only a three-month default retention window, collection must be ongoing, not retrospective. Practically: a scheduled job that snapshots `run_attempt > 1` runs (and which jobs flipped between attempts) into the repo gives Legends the flake ledger it currently lacks for near-zero compute, while practice 1 supplies the active detector.

> [!conflict]
> [[CI Run History (2026-06)]] states "the GitHub API returns only the latest attempt of each run, so earlier attempts that were re-run are invisible in this extract", while Ge & Zhang reconstructed complete rerun sequences for 155,488 rerun builds from the same API via the per-attempt endpoints keyed on `run_attempt` ^[from https://arxiv.org/html/2602.02307v1 (retrieved 2026-06-10)]. The claims reconcile — the default list endpoint returns latest-attempt records, per-attempt queries recover the rest — but the run-history page's caveat should not be read as "rerun signatures are unobtainable", only as "this extract did not query them".

### 3. Quarantine means removing from the gate, not from existence — and never silently

Google's quarantine tool "removes the test from the critical path and files a bug for developers to reduce the flakiness" — the bug is part of the mechanism, and the post immediately names the risk: quarantine "could easily mask a real race condition or some other bug in the code being tested" ^[from https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html (retrieved 2026-06-10)]. Slack's mature design suppresses *execution*, not results — their first system, which filtered flaky results out of reports, was rolled back because "failing tests were leaking into the main branch" and hiding when a test's state changed; the replacement disables the test in source via an auto-merged PR that embeds the tracking-ticket URL next to the disabled test, and suppresses only on main, never silently on PRs ^[from https://slack.engineering/handling-flaky-tests-at-scale-auto-detection-suppression/ (retrieved 2026-06-10)]. A practitioner variant keeps quarantined tests running off the critical path: move tests below a consistency threshold out of gating CI but "keep them in the reliability suite for sake of coverage and issue discovery" ^[from https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html (retrieved 2026-06-10)].

**Applicability to Project Legends:** the stack has native quarantine primitives, no external service needed. Option A (GoogleTest): rename `TEST_F(SDL2BackendTest, InputSourceInitializes)` to `DISABLED_InputSourceInitializes` with the ticket reference in a comment — "disabled tests are still compiled (and thus won't rot)", the binary prints a banner counting them, and a scheduled lane runs them anyway via `--gtest_also_run_disabled_tests`/`GTEST_ALSO_RUN_DISABLED_TESTS` ^[from https://raw.githubusercontent.com/google/googletest/main/docs/advanced.md (retrieved 2026-06-10)]. Option B (CTest): since `gtest_discover_tests` in `CMakeLists.txt` already attaches `LABELS` per target, adding a `flaky` label to quarantined tests and excluding it from gating lanes with `ctest -LE flaky` (running `ctest -L flaky` in a non-blocking nightly) keeps the quarantine list in one greppable place. GoogleTest's own tip — count `DISABLED_` occurrences with grep "as a metric for improving your test quality" ^[from https://raw.githubusercontent.com/google/googletest/main/docs/advanced.md (retrieved 2026-06-10)] — gives the quarantine-size gauge that [[Quality Gate Scripts & Hooks]] could ratchet.

### 4. The relax-the-assertion antipattern: weakened tests are quarantine without a ticket or an exit

The literature's warning is uniform: ignoring a flaky signal can bury a real defect — "If the root cause is nondeterminism in the production code, ignoring the test means ignoring a production bug" ^[from https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html (retrieved 2026-06-10)] — and even Google's mark-as-flaky mode (report failure only after 3 consecutive fails) is criticized by its own author because it "encourages developers to ignore flakiness in their own tests" and delays a real breakage signal by the full retry budget ^[from https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html (retrieved 2026-06-10)]. Slack's rollback of result-suppression makes the same point structurally: hiding failures "makes flaky test investigation difficult since there is not enough information on when the test state changed" ^[from https://slack.engineering/handling-flaky-tests-at-scale-auto-detection-suppression/ (retrieved 2026-06-10)]. GoogleTest's documented alternative for a test you cannot fix now is explicit, visible, and temporary: `DISABLED_` plus "You still have to fix the disabled tests at a later date" ^[from https://raw.githubusercontent.com/google/googletest/main/docs/advanced.md (retrieved 2026-06-10)].

**Applicability to Project Legends:** commit 911692f is the antipattern in pure form. In `tests/unit/test_pal_sdl2_backend.cpp` and `test_pal_sdl3_backend.cpp`, `EXPECT_EQ(count, 0u)` after `input->poll(events, 10)` became `(void)input->poll(events, 10)` — the assertion was deleted, so the test now verifies only that polling does not crash. Unlike a `DISABLED_` rename or a `flaky` label, this leaves no banner, no grep-able marker, no ticket, and no exit condition; the test still runs and reports green, which is precisely the "hiding test failures" failure mode Slack rolled back. The property it used to check (no spurious events queued at init) is now untested on every backend. The remediation consistent with practices 3 and 5: restore the strict assertion, quarantine the restored test (DISABLED_ or label) with a ticket, and let the burn-in lane (practice 1) qualify the fix — note 8fdd4c6 also rewrote `src/pal/sdl2/host_clock_sdl2.cpp` and `host_clock_sdl3.cpp`, so a real product-side race may already have been half-fixed without a test to confirm it.

### 5. Ownership and exit criteria: ticket on entry, owner by mapping or blame, re-qualification by repetition on exit

Entry into quarantine carries ownership metadata: Slack auto-creates a Jira ticket, assigns it via an explicit test-ownership mapping ("Create test ownership mapping to map tests to respective feature teams ... Assign a Jira ticket to the team that owns the test"), attaches the failure details, and sends weekly per-team summaries of suppressed tests ^[from https://slack.engineering/handling-flaky-tests-at-scale-auto-detection-suppression/ (retrieved 2026-06-10)]. GitHub derives the owner from history instead: an impact score (failures x branches x developers x deploys affected) crossing a threshold auto-opens an issue "assigned to the people who most recently modified either the test files or associated code prior to the test becoming flaky", so "the only person bothered by a flaky test is the person who wrote it" ^[from https://github.blog/engineering/engineering-principles/reducing-flaky-builds-by-18x/ (retrieved 2026-06-10)]. Exit is statistical, not anecdotal: Slack reruns suppressed tests "regularly in quarantine ... If they are no longer flaky then they can automatically be re-enabled" ^[from https://slack.engineering/handling-flaky-tests-at-scale-auto-detection-suppression/ (retrieved 2026-06-10)]; Spotify's Flakybot gives the same pre-merge confidence on demand by exercising the candidate fix repeatedly in the PR ^[from https://engineering.atspotify.com/2019/11/test-flakiness-methods-for-identifying-and-dealing-with-flaky-tests (retrieved 2026-06-10)]. The matching CTest exit gate is `--repeat until-fail:<n>`: n consecutive passes required ^[from https://cmake.org/cmake/help/latest/manual/ctest.1.html (retrieved 2026-06-10)]. Slack's caution for slow exits: suppressed tests rot — "a test failure can be out of date, difficult to reproduce, or the feature has evolved" ^[from https://slack.engineering/handling-flaky-tests-at-scale-auto-detection-suppression/ (retrieved 2026-06-10)].

**Applicability to Project Legends:** at this repo's scale the workflow is a convention, not a service: (a) quarantine only with a GitHub issue linked at the quarantine site (comment above `DISABLED_`/label line), owner = the committer the blame points at (for the SDL tests, that mapping is trivial); (b) the nightly quarantine lane (`ctest -L flaky` or `--gtest_also_run_disabled_tests`) keeps generating evidence; (c) exit requires the candidate fix to survive `ctest --repeat until-fail:10` (locally or in a one-off workflow-dispatch lane mirroring the asan-lifecycle job's pattern in `pal-ci.yml`) before the `DISABLED_` prefix or `flaky` label is removed and the issue closed; (d) quarantine size is reported, GoogleTest's banner and a grep count making it a one-liner in CI output.

### 6. Flakiness destroys exactly the signal test-selection and gating depend on

The cost is concentrated in transitions: at Google, "about 84% of the transitions we observe from pass to fail involve a flaky test", which trains engineers to ignore alarms and "ignore legitimate failures ... due to the high number of false-positives" ^[from https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html (retrieved 2026-06-10)]. Spotify states the endpoint: without confidence in tests "you are in no better position than a team that has zero tests" ^[from https://engineering.atspotify.com/2019/11/test-flakiness-methods-for-identifying-and-dealing-with-flaky-tests (retrieved 2026-06-10)]; GitHub frames the payoff of containment as restored signal — "red builds more meaningful. If your pull request has a failure, it's a sign you need to change something, not a sign you should hit Rebuild" ^[from https://github.blog/engineering/engineering-principles/reducing-flaky-builds-by-18x/ (retrieved 2026-06-10)]. Prioritization should follow impact, since flakiness is heavily skewed — at GitHub only 0.4% of flaky tests failed 100+ times, so "not every flaky failure should be investigated" ^[from https://github.blog/engineering/engineering-principles/reducing-flaky-builds-by-18x/ (retrieved 2026-06-10)] — and prevention should follow size, the strongest structural predictor (0.5% of small vs 14% of large tests flaky weekly; r²=0.82 against binary size) ^[from https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html (retrieved 2026-06-10)]. Mere visibility already helps: publishing a flakiness table with no enforcement cut Spotify's flakiness from 6% to 4% in two months ^[from https://engineering.atspotify.com/2019/11/test-flakiness-methods-for-identifying-and-dealing-with-flaky-tests (retrieved 2026-06-10)].

**Applicability to Project Legends:** this interacts directly with [[Test Impact Analysis & Selection (2026-06)]] — any path-based or impact-based selection scheme assumes a failure implicates the selected change, an assumption the SDL backend tests already violated (their failures were environment-conditioned, hence the relaxation). It also bears on [[Quality Gate Demotion (2026-06-08)]]: demoting a gate because its tests flake is the workflow-level analogue of 911692f, whereas quarantining the specific flaky tests (practice 3) would have preserved the gate for the stable majority. The size finding maps cleanly onto the suite's label taxonomy: expect flakiness pressure in `integration`/`ipc`-labeled targets and the SDL-stack PAL tests (real subsystem init, the analogue of Google's "large" bucket), and keep the unit lane strict rather than relaxing it to match.

> [!conflict]
> Two retry philosophies coexist in the sources. CTest's `--repeat until-pass` and GitHub's keep-the-build-green containment institutionalize in-pipeline retries ^[from https://cmake.org/cmake/help/latest/manual/ctest.1.html (retrieved 2026-06-10)] ^[from https://github.blog/engineering/engineering-principles/reducing-flaky-builds-by-18x/ (retrieved 2026-06-10)], while Micco documents that auto-retry "encourages developers to ignore flakiness" and delays true-failure signal ^[from https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html (retrieved 2026-06-10)], and Ge & Zhang show reruns are expensive and often non-diagnostic (up to 20 reruns to flip) ^[from https://arxiv.org/html/2602.02307v1 (retrieved 2026-06-10)]. The reconciliation used by GitHub and Slack: retries are legitimate as a *detector feeding a ledger and a quarantine queue* (every retried-to-green test is recorded and scored), and illegitimate as a *terminal mitigation* (retry-and-forget). For Legends, `until-pass:2` on gating lanes is acceptable only if each tolerated failure is logged as a flake event; otherwise prefer hard failure plus quarantine.
